# Quality Audit Checklist

setup 时只读审阅这些结构风险。目标不是立刻重构，而是判断 zWorkFlow 的哪些能力会被项目结构削弱，并向用户给出改进建议；本清单不授权修改项目设计或已有工作流。

## 1. 项目入口与验证

检查：

- 是否有明确运行入口
- 是否有明确测试 / build / lint / validation 命令
- 是否有 CI 或可重复验证方式

警告示例：

- 缺少验证入口会削弱 `workflow-refactor`，因为重构后无法确认行为未变。
- 缺少运行入口会削弱 `project-context`，因为 AI 无法判断真实启动链。

建议：

- 补充 README 的运行与验证命令。
- 为核心模块添加最小测试或 dry-run 验证脚本。

## 2. 架构边界

检查：

- 是否存在核心领域 / 应用层 / 表现层 / 基础设施的边界
- 是否有单向依赖规则
- 是否有编译、包、目录或命名空间约束

警告示例：

- 高代码耦合会削弱 `architecture-review`，因为模块接口无法稳定识别。
- 领域逻辑依赖 UI / 引擎 API 会削弱项目内容层复用能力。

建议：

- 提炼核心规则层。
- 通过目录、程序集、包或模块边界强化依赖方向。
- 为跨层调用建立 adapter / port。

## 3. 可复用工具与重复逻辑

检查：

- 是否存在大量重复 helper / conversion / loading / event / validation 逻辑
- 是否缺少通用工具类或服务
- 是否工具类过度膨胀，变成无边界杂物箱

警告示例：

- 缺少可复用工具类会削弱 `workflow-refactor`，因为重复逻辑无法安全集中。
- 工具类过度膨胀会削弱 `architecture-review`，因为它隐藏了真实领域边界。

建议：

- 把重复逻辑按领域或能力提炼为小而深的模块。
- 避免创建全局万能工具类；优先命名具体职责。

## 4. 文档与代码一致性

检查：

- README / docs 是否描述当前代码
- 是否有过时路径、过时 API、过时架构图
- 是否有文档索引或入口

警告示例：

- 文档与代码冲突会削弱 `project-doc-sync` 和 `project-context`，导致 AI 按旧事实工作。
- 整个框架只生成一个工程能力节点会隐藏模块级职责和依赖；README 核心模块表与代码目录一致时必须逐模块建条目。
- 新增工具类 Architecture 若缺少基于实际入口、所有权和生命周期证据生成的中英文使用策略，setup 视为能力目录不完整；已有策略被重复 setup 覆盖也属于失败。
- 文档包账本若包含项目绝对路径、项目包会写回账本，或文档修改会自动触发设计导入/proposal，视为包边界失败。项目端必须在关键文件验证成功后才保存绑定并点亮桥接灯；结构视图需覆盖未登记文档、实现进度、实现后变更和摘要，并能把尚未登记摘要的外部指纹变化显示为“手动修改”。
- 工具专属目录仍保存完整 Skills、项目代码流程或机器绝对 memory 路径，说明迁入/薄化事务未完成。

建议：

- 建立文档索引。
- 用 `project-doc-sync` 在每次较大改动后同步文档。
- 对无法确认的内容标记“待确认”，不要写成事实。

## 5. 数据、资源与配置

检查：

- 配置、资源、运行时状态是否混在一起
- 是否有资源路径硬编码
- 是否有明确加载 / 释放 / 生命周期规则

警告示例：

- 资源路径散落会削弱项目架构 skill，因为新增功能难以判断资源生命周期。
- 配置和运行时状态混用会增加迁移和存档风险。

建议：

- 建立配置入口和资源加载约定。
- 将运行时状态与静态配置分离。

## 6. Agent 工作流共存与成本

检查：

- 是否已有 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 或工具专属入口
- 是否已有 `.agents/`、`.claude/`、`.codex/`、`.cursor/`、`.github/agents/`、`.gemini/`、`.windsurf/`、`.kimi-code/`
- 团队成员是否使用不同 AI 工具；仓库是否错误保存了唯一 active tool
- 当前工具是否能直接发现 `.agents/skills/`，或需要薄 wrapper / 版本降级
- 是否有重复或冲突的工作流规则
- 是否有机器绝对路径
- 是否每个任务都会重复读取大体积入口或 skills
- 是否能用来源指纹和精简摘要避免重复扫描
- 子 Agent 是否支持独立选模、runtime 是否能提供实际可用选项、当前成员是否已有本地成本/质量偏好
- 是否把便宜模型误写成“必然减少 token”，或为了拆 Agent 重复读取同一批上下文

警告示例：

- 多套入口规则冲突会让 zWorkFlow 无法安全选择路由。
- 机器绝对路径会让已有能力难以复用。
- 重复加载等价工作流会增加延迟和 token 消耗。
- 把个人工具选择提交到仓库会导致不同成员互相覆盖 setup 状态。
- 根据平台名称猜测模型 ID 可能写入当前账号不可用的配置；逐 Agent 能力无法验证时应降级而不是伪装成功。

zWorkFlow 处理：

- 生成只读能力映射，等价能力标记 `reuse-existing`。
- 将冲突与绝对路径作为建议报告，不修改来源文件。
- 记录来源指纹；未变化时后续只读取精简路由摘要。
- 按 `setup/adapters/registry.json` 记录各工具的能力可达方式；个人工具和版本只写入 Git 忽略的本地选择文件。
- 按 role profile 生成模型需求；仅对已验证映射或唯一运行时候选自动选模，歧义由当前成员确认一次。
