# OpenSpec Intake Gate

这是功能性游戏内容或运行框架改动前的需求入口审阅。框架代码改变运行能力或公共契约时必须进入；只调整内部实现且保持功能与契约不变时不进入。本 gate 不创建 OpenSpec artifact，也不依赖 CLI。

## 何时触发

只有同时满足以下条件时才触发：

- 请求会产生持久改动，且不是小型、局部、低风险的改动。
- 改动对象是游戏内容代码实现，或承载游戏代码运行的框架及运行基础。
- 改动意图会新增或改变玩法功能、交互语义、数据兼容性或公共运行契约；仅改变“如何实现”或非权威视觉呈现不满足此条件。
- 游戏内容包括玩法机制、规则、关卡/流程、角色/敌人/卡牌/物品、叙事文案，以及会改变玩家操作或反馈语义的游戏内 UI。

不触发 zWorkFlow，直接按任务对应的普通工作流处理：

- 不改变项目运行框架的 Unity/引擎适配、第三方依赖接入和通用基础设施。
- 编辑器工具、构建工具、开发工具、工作台及其配置。
- 任何工作流优化或维护。
- 纯 View 层非权威视觉表现，例如装饰性位置/旋转、颜色、粒子、镜头抖动和不改变交互判定的动画；前提是不改变玩法结果、输入命中、反馈语义、可访问性、持久化数据或公共契约。
- 不改变功能、外部行为或公共契约的纯重构、架构整理、性能优化、代码清理、测试和文档维护。
- 实现方案调整、类/文件搬移、分层重排、抽象替换和内部调度改写，只要验收目标是行为保持，就走普通实现/重构流程。
- typo、注释、日志文本、单行无行为变化改动，以及其他边界清晰的小型改动。
- 纯提问、解释、只读审查和状态查询。

无论任务类型如何，用户显式调用 zWorkFlow、OpenSpec、OPSX 或对应 skill/指令时，按显式请求进入流程。单独说明改动位于“框架代码”只表示代码归类，不再自动覆盖行为保持判断。

## 边界判断

- “修改游戏规则如何计算命中”属于游戏内容；“优化命中计算的内部结构且行为不变”属于纯重构。
- “新增玩家可使用的卡牌筛选功能”属于游戏内容；“改进 Unity 编辑器内的卡牌配置工具”属于工具。
- “改变受击提示所表达的可行动状态”属于交互语义；“给卡堆厚度层增加装饰性随机旋转”属于纯 View 层表现。
- “改变公共状态机或模块生命周期契约”属于功能性框架改动；“重写其内部实现但保持状态、事件顺序和公共契约”属于行为保持型重构。
- 同一请求同时包含游戏内容/框架与工具/引擎改动时，只对非平凡的游戏内容和框架部分使用 zWorkFlow；其余部分作为实现任务或依赖记录。

## View 层轻量需求澄清

纯 View 层表现不创建 OpenSpec 工件。实现前仍在对话中确认作用对象、参数范围、刷新时机、默认行为、不影响的逻辑和验收条件；信息已清楚时总结后直接实现，不要求用户重写模板。

## 通过条件

用户请求必须能明确回答：

1. 目标：要达成什么结果
2. 背景 / 动机：为什么要改
3. 修改范围：改哪些系统、文件或能力
4. 约束 / 不做什么：边界、兼容性、禁止项
5. 验收标准：什么情况算完成

如果用户的描述已经隐含满足这些项，可以继续，不必形式主义要求重写。

## 未通过时的输出

未通过时停止执行，不读取/修改业务文件，并输出：

```text
⚠️ 需求未通过 OpenSpec Intake Gate，暂不执行修改。

缺失项：
- 目标：
- 范围：
- 验收标准：

请按下面格式重新描述：
1. 目标：
2. 背景 / 为什么要改：
3. 修改范围：
4. 不做什么：
5. 验收标准：
```

只列真实缺失项。不要把已经清楚的信息重复列为缺失。

## 与 OPSX 的关系

- 边界清晰的小型实现不触发 gate，直接实现。
- 用户要求正式 proposal/change：通过 gate 后调用 `openspec-propose`。
- 实现中发现设计变化：暂停并建议使用 `openspec-update-change`。
- 完成后要同步或归档：使用 `openspec-sync-specs` 或 `openspec-archive-change`。
