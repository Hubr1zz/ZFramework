# Skill: 代码重构

## 概述

当需要对现有代码进行质量检查、识别问题、执行重构操作或评审重构方案时使用本 skill。

覆盖范围：重构原则与边界判断、6 类检查目标、24 种坏味道识别、60+ 具名重构手法、操作流程与风险控制、人机协作协议。

---

## 一、核心原则

- **不改变外在行为**：重构只改内部结构，不添加新功能，两件事不能同时进行（两顶帽子）。
- **小步前进**：每次只做一件事并及时验证。失败时先定位本步影响；只安全撤回自己的独立改动，不覆盖用户或他人修改。
- **有明确收益才动**：只进行风险可控、收益清晰的改动，避免无关的大规模重写。
- **先读后改**：修改前必须已阅读项目结构和上下文关键代码，理解相关功能，遵循现有代码风格。
- **用工具确认**：删除前用索引、`rg` 和项目资源引用核验；Unity 序列化、反射或动态注册不能仅凭文本搜索判定未使用。

## 二、检查目标（6 类）

每次重构任务按以下 6 类逐项检查：

| # | 类别 | 检查内容 |
|---|------|----------|
| 1 | **冗余与重复** | 重复逻辑、过时实现、死代码、已被新实现替代但未清除的旧代码 |
| 2 | **失效分支** | 不再触发的 fallback、兼容分支、已废弃的降级路径 |
| 3 | **硬编码** | 硬编码的配置、路径、数值、字符串、资源引用；改为常量、配置、序列化字段、ScriptableObject 或项目已有配置机制 |
| 4 | **命名与结构** | 命名不清晰、职责划分不明、与最新设计或项目风格不一致 |
| 5 | **维护性与扩展性** | 耦合严重、职责不清、可简化但未简化的实现 |
| 6 | **性能** | 有明确更优解的性能问题（先 profiling 确认热点，不过早优化） |

### 项目特定结构检查（在六类之外补充扫描）

- **动态生成的 UI / 布局**：发现用代码 `new GameObject` + `AddComponent` 现搭 UI 层级、控制布局的（非单元测试用途），标记为可配置化改造点 —— 应改为 Prefab + `[SerializeField]` 引用；数据驱动列表项改为「模板 Prefab + `Instantiate` + `Bind`」。这类改造会改变运行时行为（需配合编辑器搭 Prefab），属「⏸ 需用户确认」类，不直接改。
- **文件 / 类的归属**：检查是否有类放在语义不合适的脚本或目录（如 MonoBehaviour 放在 SO/ 下、数据类与控制器混在一起、一个文件塞多个不强相关的类）。判断标准是「开发者能否快速理解系统、定位文件」。跨命名空间搬移属高风险，记为建议；同命名空间分文件属低风险，可直接做。

## 三、24 种代码坏味道（识别触发器）

识别坏味道是重构的第一步。

### 命名与可读性
| 坏味道 | 描述 | 推荐手法 |
|--------|------|----------|
| 神秘命名 | 变量/函数名无法表达意图 | 改变函数声明、变量改名、字段改名 |
| 注释 | 用注释补救烂代码（注释本身不是坏味道，代替好命名才是） | 提炼函数、改变函数声明 |

### 重复与冗余
| 坏味道 | 描述 | 推荐手法 |
|--------|------|----------|
| 重复代码 | 相同代码出现多处 | 提炼函数、函数上移、移动语句 |
| 冗赘的元素 | 不再有用的函数/类/变量 | 内联函数、内联类、移除死代码 |
| 夸夸其谈通用性 | 过度设计，为"将来可能"添加的抽象 | 折叠继承体系、内联函数、移除死代码 |

### 函数与参数
| 坏味道 | 描述 | 推荐手法 |
|--------|------|----------|
| 过长函数 | 函数做了太多事 | 提炼函数、引入参数对象、以查询取代临时变量 |
| 过长参数列表 | 参数超过 3-4 个 | 引入参数对象、保持对象完整、以查询取代参数 |
| 临时字段 | 某些字段只在特定情况下有值 | 提炼类、引入特例 |

### 数据
| 坏味道 | 描述 | 推荐手法 |
|--------|------|----------|
| 全局数据 | 全局变量可被任何地方修改 | 封装变量 |
| 可变数据 | 数据被随意修改，难以追踪 | 封装变量、拆分变量、将引用对象改为值对象 |
| 数据泥团 | 总是一起出现的数据字段 | 引入参数对象、封装记录、提炼类 |
| 基本类型偏执 | 用原始类型代替小对象（如金额用数字而不是 Money 类） | 以对象取代基本类型、引入参数对象 |
| 纯数据类 | 只有 getter/setter、没有行为的类 | 搬移函数（将行为移进来） |

### 职责与依赖
| 坏味道 | 描述 | 推荐手法 |
|--------|------|----------|
| 依恋情结 | 函数对其他类的数据比自己类更感兴趣 | 搬移函数、提炼函数 |
| 发散式变化 | 一个类因多种不同原因被修改 | 提炼类、拆分阶段 |
| 霰弹式修改 | 一个变化需要修改多个类 | 搬移函数、搬移字段、函数组合成类 |
| 内幕交易 | 两个类之间过度交换私有数据 | 搬移函数、搬移字段、隐藏委托关系 |
| 过大的类 | 单个类承担过多职责 | 提炼类、提炼超类 |

### 控制流
| 坏味道 | 描述 | 推荐手法 |
|--------|------|----------|
| 重复的 switch | 相同的 switch 逻辑散落各处 | 以多态取代条件表达式 |
| 循环语句 | 循环使逻辑难以理解 | 以管道取代循环（map/filter/reduce） |

### 继承相关
| 坏味道 | 描述 | 推荐手法 |
|--------|------|----------|
| 过长的消息链 | a.b().c().d() 的长调用链 | 隐藏委托关系、提炼函数 |
| 中间人 | 类的大多数方法都委托给另一个类 | 移除中间人、内联函数 |
| 异曲同工的类 | 接口不同但功能相似的类 | 改变函数声明、搬移函数、提炼超类 |
| 被拒绝的遗赠 | 子类不想要父类的方法/数据 | 以委托取代子类/超类 |

## 四、重构手法速查（按场景）

### 提取与合并
| 手法 | 何时用 |
|------|--------|
| **提炼函数**（Extract Function） | 一段代码可以被命名解释意图时 |
| **内联函数**（Inline Function） | 函数太简单，间接层没有价值 |
| **提炼变量**（Extract Variable） | 复杂表达式，给中间结果命名 |
| **内联变量**（Inline Variable） | 变量名没比表达式更好说明意图 |
| **提炼类**（Extract Class） | 一个类承担了两个类的职责 |
| **内联类**（Inline Class） | 一个类做的事太少 |
| **提炼超类**（Extract Superclass） | 两个类有相似特性 |

### 搬移
| 手法 | 何时用 |
|------|--------|
| **搬移函数**（Move Function） | 函数与另一个上下文的交流更多 |
| **搬移字段**（Move Field） | 字段在另一个类中使用更频繁 |
| **搬移语句到函数** | 某些语句总是和函数调用一起出现 |
| **搬移语句到调用者** | 函数功能应由调用者负责一部分 |

### 重命名
| 手法 | 何时用 |
|------|--------|
| **改变函数声明** | 函数名/参数名无法清晰表达意图 |
| **变量改名** | 变量名无法解释其用途 |
| **字段改名** | 字段名需要更好反映其含义 |

### 封装
| 手法 | 何时用 |
|------|--------|
| **封装变量** | 暴露的字段需要增加访问控制 |
| **封装记录** | 简单数据结构需要行为 |
| **封装集合** | 集合属性被外部直接修改 |
| **以对象取代基本类型** | 基本类型有行为/约束需要表达 |

### 简化条件
| 手法 | 何时用 |
|------|--------|
| **分解条件表达式** | 复杂条件逻辑，提炼成有意义的函数 |
| **合并条件表达式** | 多个条件有相同结果，可合并 |
| **以卫语句取代嵌套条件** | 深层嵌套的 if-else，用 early return |
| **以多态取代条件表达式** | switch/if 按类型分发行为 |
| **引入特例**（Null Object） | 对特殊值（如 null）反复做相同检查 |
| **引入断言** | 代码运行依赖某种假设，显式声明 |

### API 重构
| 手法 | 何时用 |
|------|--------|
| **将查询与修改分离** | 一个函数既有副作用又返回值 |
| **函数参数化** | 多个函数逻辑相似，只是某个值不同 |
| **移除标记参数** | 布尔参数控制函数内部行为 |
| **保持对象完整** | 从一个对象取多个值传给函数，不如直接传对象 |
| **以工厂函数取代构造函数** | 构造过程需要更多灵活性 |
| **以命令取代函数** | 需要撤销、参数构建、或更复杂的生命周期 |

### 继承处理
| 手法 | 何时用 |
|------|--------|
| **函数上移 / 字段上移** | 子类中有相同方法/字段 |
| **函数下移 / 字段下移** | 超类中的行为只与部分子类相关 |
| **以子类取代类型码** | 类型码影响类的行为 |
| **移除子类** | 子类承担的变化不够多 |
| **以委托取代子类/超类** | 继承关系不再合适，应改用组合 |

## 五、操作流程

```
1. 阅读项目结构与上下文关键代码，理解相关功能
   ↓
2. 按六类检查目标逐项扫描，识别坏味道
   ↓
3. 对每个问题：判断是否满足"直接修改"条件（见下方决策规则）
   ↓
4. 可直接修改的：选择对应手法，小步执行，每步后运行测试
   ↓
5. 需暂缓或确认的：注释/记录，纳入总结等待用户确认
   ↓
6. 运行项目已有的验证、测试或 batch validation，确认未破坏现有功能
   ↓
7. 输出总结（格式见末节）
```

## 六、决策规则

### ✅ 可直接修改
- 明确无用的死代码，且 `rg` 搜索确认无引用
- 硬编码改为常量/配置，且确认改法与项目现有机制一致
- 低风险命名修正（局部变量、私有函数）
- 简单的提炼函数、卫语句替换、合并条件等结构性整理

### ⏸ 暂缓并等待用户确认
以下情况不修改代码，只记录疑虑并在总结中列出：

| 情况 | 处理方式 |
|------|----------|
| 未被使用，但不确定是否旧代码 | 记录疑虑与核验结果 |
| 冗余/重复代码，不确定是否有隐含差异 | 标注两处差异点 |
| 不确定硬编码是否合理（可能是有意为之） | 记录为疑问 |
| 需要大规模重写（框架级、大功能模块） | 不修改，记录为建议 |
| 风险较高或无法判断风险的重构点 | 记录为建议 |

### ❌ 不应重构
- 代码即将被删除/替换
- 距离发布极近且测试不充分
- 改动成本远超收益（遗留系统边缘代码、外部 API 适配层）

### 优先级顺序
1. 命名修正（最低风险，收益最高）
2. 提炼函数（减少理解负担）
3. 搬移与封装（理清职责）
4. 继承/多态重构（最大改动，最后处理）

```
- ...

### 建议（未修改）
- [文件/类] xxx 职责过重，建议拆分为 A / B 两个类，涉及改动较大

- ...
```
