# Project Refactor Queue

这是可选的 zWorkFlow 项目内容层 skill。只有能力映射未发现等价维护队列且目标路径未占用时才使用空白模板；不得复制、替换或改写已有队列。

## 必读参考

- [PROTECTED_FILES.md](references/PROTECTED_FILES.md)：仅在可能修改项目文件时读取
- [REFACTOR_QUEUE.md](references/REFACTOR_QUEUE.md)：仅在增量重构、处理技术债或用户查看队列时读取

安装后，两个 reference 分别是保护清单和待处理队列的唯一权威数据源。工具专属目录只能放薄转接口，不得保存副本。

## 使用规则

- 可能修改项目文件时只读取 `PROTECTED_FILES.md`，不要因此加载重构队列。
- 只有增量重构、处理技术债或用户明确查看队列时才读取 `REFACTOR_QUEUE.md` 的待处理区块。
- 普通功能开发和行为保持型重构不维护“近期改动模块”或队列内决策日志；近期范围按需从 Git 获取。
- OpenSpec `apply` 的正常代码、测试和任务完成记录不复制到本队列；它们分别由源码、Git 与活动 Change 记录。只有 apply 中新发现、经确认延期且仍需后续处理的技术债、非功能重构或架构风险，才新增或更新一个可执行队列条目。
- 架构/功能决策写入 ADR 或 OpenSpec；可复用规则与排障约束写入其所属 skill/reference，其余依赖 Git/任务记录，不建立重复记忆池。
- 每个条目必须使用工作台支持的状态：`待处理`、`进行中`、`已维护`；暂缓原因写入维护备注，不新增状态值。
- 当某条待优化内容被重构或以其他方式处理完，必须把该条目的 `状态` 改为 `已维护`，并记录 `维护人` 与 `维护时间`。
- `维护人` 可填写执行者身份，例如 `codex`、`claude`、`cursor`、`copilot`、`gemini`、`windsurf`、`kimi`、具体账号名或团队成员名；如果无法确认，写 `未注明`，不要留空。
- 维护人解析顺序：
  1. 若项目存在 `.agent-memory/team/MAINTAINERS.md`，优先按其中的账号 / 环境变量 / 工具身份映射填写。
  2. 其次使用当前工具可得的账号、会话身份或环境名，例如系统用户名和当前适配器暴露的会话身份。
  3. 如果识别到账号 / 环境名但映射表中没有对应昵称，并且当前任务可以向用户确认，必须先询问用户希望使用的维护昵称；得到昵称后，将映射追加到 `.agent-memory/team/MAINTAINERS.md`，本次及后续维护记录都使用该昵称。
  4. 如果只能确认工具，写适配器注册表中的稳定 tool id；不要把某个工具身份当作团队默认身份。
  5. 如果连工具身份也无法可靠确认，或任务处于非交互环境无法询问用户，临时写 `未注明`，并在 `维护备注` 中说明“维护人未能自动识别 / 未能确认昵称”。
- 不要声称自动识别到无法验证的真实成员；真实姓名、团队昵称和账号映射必须来自用户或 `.agent-memory/team/MAINTAINERS.md`。
- 更新条目时保留历史描述，不要删除原始问题；如需说明处理方式，在 `维护备注` 追加简短说明。
- 高风险建议只记录，不擅自执行。

## 条目字段

推荐字段：

```markdown
### [优先级: 中] 简短标题
- **文件**: `Assets/Scripts/Xxx/Yyy.cs`
- **类型**: 职责 / 命名 / 性能 / 硬编码 / 文档
- **描述**: 具体问题说明
- **来源**: 第N次重构总结 / 用户手动添加
- **状态**: 待处理
- **维护人**: 未注明
- **维护时间**: 未维护
- **维护备注**: -
```
