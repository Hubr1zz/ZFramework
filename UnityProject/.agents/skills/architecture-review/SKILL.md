# Game Architecture Review

发现能提高局部性、可测试性和 Agent 可导航性的架构改进。默认只审查和给出候选；用户明确要求实现后才改代码。行为保持型架构重构不进入 OpenSpec；若候选会改变玩法、交互语义、数据兼容性或公共运行契约，转交 `openspec-intake-gate`。

## 最小上下文

1. 先读项目索引，只读取命中的架构/领域资料和相关 ADR。
2. C# 结构索引可用时先用 `codebase-query` 收敛类型、调用者和影响范围，再读候选源码。
3. Unity 隐式引用不能仅靠 C# 索引下结论；按影响检查 `.asmdef`、`.meta`、Prefab、Scene、ScriptableObject、Addressables 或其他资源配置。
4. 使用 [LANGUAGE.md](LANGUAGE.md) 的 module、interface、depth、seam、adapter、leverage、locality 术语，但项目领域命名优先于通用架构词。

## 游戏开发审查维度

- **权威状态**：玩法规则、运行时状态、ScriptableObject 配置和 View 是否各有唯一权威；是否存在双写或表现层反向决定规则。
- **依赖方向**：纯 C# 规则层是否依赖 Unity API；asmdef、Editor/Runtime、Adapters/View 的方向是否清楚。
- **生命周期**：`Awake`/`OnEnable`/`Start`、场景切换、Domain Reload、对象销毁与异步取消是否泄漏到领域接口。
- **序列化兼容**：字段重命名、类型移动、GUID、存档 schema、Prefab/Scene 引用是否让“普通重构”变成数据迁移。
- **协调复杂度**：EventBus、状态机、回合/时点、动画与异步流程的顺序和所有权是否集中。
- **资源边界**：资源加载、Addressables、实例化/释放与缓存策略是否位于明确模块，而非散落调用者。
- **测试接缝**：规则能否脱离 Unity 运行；引擎适配是否可用 EditMode/PlayMode 或少量集成测试覆盖。

## 候选门禁

只有存在源码或资源证据时才提出候选，并至少满足一项：

- 同一行为变化需要修改多个调用者或多个表现入口。
- 引擎生命周期、序列化或资源细节通过接口泄漏。
- 状态所有权不清导致重复状态、顺序依赖或难以复现的 bug。
- 无法在稳定接口处测试，只能依赖脆弱的内部实现断言。

对浅模块使用删除测试：删掉它后复杂性若只搬到调用者，它有加深价值；复杂性直接消失则可能只是多余间接层。不要为单一实现预建接口，也不要把 MonoBehaviour、ScriptableObject 或 EventBus 包一层就称为架构改进。

## 输出

直接在对话中给出最多 3–5 个候选，不生成 HTML 报告或仓库内审计文件。每个候选包含：

- 证据：文件/资源与具体摩擦。
- 建议：模块如何加深、权威状态放在哪里。
- 收益：局部性、杠杆、测试面如何变化。
- Unity 风险：序列化、生命周期、场景/Prefab、asmdef 或主线程约束。
- 强度：`Strong`、`Worth exploring`、`Speculative`。

最后明确推荐优先候选；没有足够证据时直接报告“未发现值得架构重构的候选”。

## 选中候选后的接口设计

至少比较两种方案：最小接口，以及为最常见调用路径优化的接口；只有真实存在两个实现（通常是生产实现与测试/平台实现）时才引入 seam/adapter。

- 纯规则和内存状态直接放入深模块，不为测试制造端口。
- Unity API、时间、输入、资源和持久化留在适配层；领域层接收最小数据或意图。
- 第三方/远程 I/O 只有确需替换时才定义端口。
- 测试针对公开行为和不变量；不得为重构删除有效行为断言。

比较 depth、locality、序列化兼容和迁移成本，给出一个有主见的推荐。只有上下文独立且当前工具允许时才用子 Agent 并行探索，不把并行作为接口设计前置条件。
