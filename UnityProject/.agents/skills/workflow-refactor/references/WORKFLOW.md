# Skill: Agent 工作流与实现规范

> 开工前按需读取。实现新功能、执行重构时遵循本文件；权限边界与文档路由见根 `AGENTS.md` 或当前工具的专属薄入口。

---

## 任务类型与 Agent 分配

| 用户指令 | 主 Agent | 执行 Agent |
|---|---|---|
| "实现 [功能]" / "新功能" | 设计、协调、审查 | 边界清晰的代码实现 |
| "重构" / "优化" / "维护" | 扫描、决策、风险控制 | 低风险执行 |
| "增量重构" | 读队列、决策、审查 | 低风险执行 |

**执行 Agent 可独立执行**（无需主 Agent 逐行决策）：
- 命名修正（局部变量、私有方法）
- 硬编码提取为项目中已存在的常量/配置字段
- 简单提炼函数（<30 行，无跨文件依赖）
- 格式整理、注释补充

**必须由主 Agent 决策**：
- 跨文件 / 跨系统的搬移或重构
- 新增类、接口、抽象层
- 涉及 EventBus 事件或状态机的改动
- 任何「⏸ 暂缓确认」类问题的处置

> Agent 委派是可选执行方式，不绑定具体模型。当前工具不支持委派、并发价值不高，或用户未授权委派时，由主 Agent 按同一流程完成全部工作。

## 流程一：新功能开发

```
1. [主 Agent] 读取当前工具入口文档 + 相关模块文件，理解上下文
   ├─ 有不确定的需求细节 → 询问用户，等待答复后再继续
   └─ 需求明确 → 继续

2. [主 Agent] 评估相关系统是否存在结构层面的优化机会
   ├─ 有 → 告知用户重构方案，等待确认后再实现功能
   └─ 无 → 继续

3. [主 Agent] 输出实现方案（涉及文件、新增类/方法、设计决策）

4. [执行 Agent / 主 Agent] 执行代码实现
   - 遵循现有代码风格
   - 需求未描述的细节：保证可扩展性，留空占位，不擅自补全

5. [主 Agent] Review 实现结果，确认符合架构要点和命名规范

6. 不为普通功能开发读取或更新重构队列；近期改动需要时从 Git diff/log 获取
```

## 流程二：手动触发重构

```
1. [主 Agent] 读取以下文件建立上下文：
   - 根 `AGENTS.md` 或当前工具专属薄入口
   - `.agents/skills/project-context/references/PROJECT-INDEX.md`
   - 任务涉及序列化、动画、资源、启动、依赖注入、异步或编辑器扩展时读取 `.agents/skills/project-tooling/SKILL.md`，只加载命中的工程能力条目
   - 只在索引命中时读取对应 `project-domain-*` 领域参考；跨系统架构任务才读取项目架构文档
   - `.agents/skills/project-refactor-queue/references/PROTECTED_FILES.md`（只读取保护清单）
   - `.agents/skills/project-refactor-queue/references/REFACTOR_QUEUE.md` 的「待处理队列」（仅增量重构/技术债任务读取）
   - `.agents/skills/workflow-refactor/references/Optimize.md`（重构规范）

2. [主 Agent] 确定本次扫描范围：
   - 用户指定范围 → 按指定范围
   - "增量重构" → 优先处理「📋 待处理队列」，近期范围按需从 Git diff/log 获取
   - "全量重构" → 按 Optimize.md 六类检查目标全量扫描

3. [主 Agent] 扫描代码，对每个问题分类：
   ✅ 低风险 → 交由执行 Agent 或主 Agent 执行
   ⏸ 需确认 → 不改代码，记入总结
   ❌ 建议   → 不修改，记入总结
   （使用 rg 确认引用；跳过受保护文件）

4. [执行 Agent / 主 Agent] 执行低风险修改

5. [主 Agent] 运行项目已有验证 / Unity batch validation，确认未破坏现有功能

6. [主 Agent] 更新 `.agents/skills/project-refactor-queue/references/REFACTOR_QUEUE.md`：
   - 已处理的队列项 → 从「📋 待处理队列」移除
   - 「⏸ 注释暂留」和「❌ 建议」条目 → 写入「📋 待处理队列」
   - 不追加通用重构流水账；可复用规则或排障约束写入其所属 skill/reference，承重架构/功能决策写 ADR 或 OpenSpec，其余依赖 Git/任务记录

7. [主 Agent] 输出重构总结（格式见 `.agents/skills/workflow-refactor/references/Optimize.md` 末节）
```

## 证据优先验证

修改前在方案或现有 OpenSpec 工件中写清可观察行为、不应改变的不变量和拟执行验证；不为普通任务新增独立 SPEC/EVIDENCE 文件。验证强度按风险升级：

- **轻量**：文档、命名、局部配置；运行定向静态检查或说明为何不适用。
- **常规**：Bug、普通功能或跨文件重构；先让 Bug 回归测试失败，再实现；完成后运行相关测试和项目编译。
- **高风险**：存档/序列化、公共契约、并发/异步、状态机、资源生命周期或跨平台兼容；先列失败模式，再增加能捕获对应风险的测试或实机检查。

Unity 项目按改动选择验证层，不把纯 C# 单元测试当作引擎行为证据：

- GameCore/纯规则：单元测试与程序集编译。
- MonoBehaviour、Editor 工具、序列化：Unity 脚本编译和相关 EditMode 测试。
- 场景、Prefab、输入、动画、资源或生命周期：相关 PlayMode/实机路径；无法执行时标为 `unverified`。
- `.asmdef`、GUID、资源路径、存档 schema：定向兼容检查，并明确未覆盖的旧资产/旧存档范围。

交付只引用最后一次代码修改后的真实结果。每项状态使用 `pass`、`fail`、`unverified` 或 `n/a`，给出实际命令/入口和数字；不得把未运行、旧结果或静态推断写成通过。仓库已有失败先记录基线，要求本次修改不增加新失败，不顺手修复无关问题。

## 新功能实现规范

- 实现前确保完全理解需求，不确定的细节先询问用户
- 实现前理解相关上下文，优先复用已有代码风格和设计
- 需求未描述的细节：保证可扩展性，具体内容留空，不额外实现
- 实现前评估相关系统是否合理；有结构层面优化方案时，先告知用户而不是直接实现

### 大功能拆分与确认

- 规模较大的功能：先拆成小功能，梳理清触发链与各模块职责，逐项与用户确认细节后再推进
- 不要为了一次做完而跳过确认，把需求未明确的细节擅自补全；宁可分步确认也不要大批量实现后才发现方向偏差

### 避免动态生成（尤其 UI）

- **除单元测试外，不用代码控制布局 / 动态生成固定 UI 层级**。固定布局应做成 Prefab，或在场景中提前配置好，由高层脚本持有引用并调用控制。
- 需要持有的引用（TMP、Image、GameObject、Button、RectTransform 等）一律用 `[SerializeField]` 暴露给 Inspector，由用户拖拽连线
- **数据驱动的列表项**（数量随数据变化，如背包条目、角色行）：做成「模板 Prefab + 运行时 `Instantiate` + 脚本 `Bind(数据)`」；承载它们的容器 / 槽位区域做成可提前配置的物体（尺寸、位置、上限可在编辑器快速编辑），而非代码现搭。

### Unity 组件与配置边界

- 玩法规则、状态与可测试编排优先写成高内聚纯 C# 对象；`MonoBehaviour` 只负责生命周期、Unity API、场景引用、输入表现适配与系统装配。
- 优先让现有系统级 Manager / presenter / composition root 持有适配器，不为每个新小功能增加一个需要散落挂载的组件。新增组件必须有独立生命周期或明确场景身份。
- 同一系统的策划参数集中到少量 ScriptableObject / 配置对象，并在边界处映射为运行时定义；不要把相关参数分散到多个场景物体。运行时权威状态不存入 ScriptableObject。
- 设计与交付时明确列出真正需要开发者完成的 Inspector 引用、可调参数、Prefab/场景安装和首次使用入口；没有人工操作就不要制造空指引或多余暴露字段。

### 文件与类的组织

- 通用接口类（如 `IGameState` 里的一组状态接口）可放同一脚本；与主类强相关、或只服务于主类的特定类，也可与主类同脚本
- 但要判断**语义是否合适**，并遵守**文件名规范**（文件名应反映其主要内容）
- 组织的核心目的：**让开发者能快速理解系统、快速定位文件**。以此为准绳决定「合并到同一脚本」还是「单独拆出脚本」
