# Formal Spec Scope

`openspec/specs/` 只维护构成已发布游戏玩法与玩家运行时的定义，不是“项目中所有已实现能力”的目录。

## 准入条件

一个 capability 只有同时满足以下条件，才可以生成 Delta、正式 Spec 或关系图谱节点：

1. 它定义玩家可观察的玩法规则、游戏流程、交互语义、内容数据契约，或这些能力在 Player 构建中依赖的稳定运行时契约。
2. 移除它会改变游戏可玩行为、存档/配置兼容性、玩家可观察结果，或使上述玩法运行时契约失效。
3. 它能以游戏领域能力命名，而不是以某个编辑器窗口、Agent 工作流、索引器、构建器、调试器、测试工具或维护任务命名。

运行时桥接只有在进入 Player 构建且是游戏启动、生命周期或玩法正确性的稳定契约时，才可作为 `system`。仅用于开发提效、编辑器展示、生成代码、构建、测试、调试或工作流维护的能力不得借 `system` 分类进入正式 Spec。

## 明确排除

- zWorkFlow / OpenSpec 自身的工作台、布局、页面和工作流规则；
- C# 派生索引、代码搜索、Agent memory、Skill、适配器及其他开发者效率工具；
- Unity Editor 扩展、导入器、构建/发布工具、测试基础设施和调试面板；
- 行为保持型重构、性能优化、文档维护与内部实现细节。

用户显式要求 OpenSpec 或“生成正式 Spec”不会覆盖此边界。对于被排除能力，应改写对应 Skill、zWorkFlow 文档/测试或 `project-tooling` 工程能力记录；不得创建占位 Delta、正式 Spec、`spec-review.json` 或依赖图节点。

## 混合改动

同一任务同时修改玩法与开发工具时，只为玩法/玩家运行时 capability 创建 Change 与正式 Spec。工具改动可以作为实现支撑写入玩法 Change 的设计说明或任务，但不得被提升为独立 Spec capability。sync 前再次执行本门禁；发现越界 Delta 时停止同步并先把它移出 Change。
