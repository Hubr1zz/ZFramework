# Hunting in Darkness 可游玩里程碑记录

更新日期：2026-08-18

## 本轮完成

- 通过 ZFramework 启动场景自动装配现有 `GameManager`，保留现有三阶段状态机作为唯一流程权威。
- 增加可序列化的启动配置与狩猎内容目录，内容不再由测试入口或场景临时对象硬编码。
- 配置无火营地、雕像平原、蘑菇林、破碎废墟、浅水沼泽五类地块，以及碎石、柔软器官、蘑菇肉三类基础素材。
- 增加可操作的营地 HUD：显示年份、狩猎史、资源库存、猎人属性，并允许选择 1—4 名猎人通过正式 `TryDepart` 流程出发。
- 增加营地开局内容目录与三份 `HunterData`，默认猎人不再使用全零属性；初始库存与狩猎素材统一使用同一批 `ItemData`。
- 跑通营地出发、六边形地图翻牌、资源点生成、翻牌采集、主动撤退入库、地图 Boss 遭遇、Boss 回合与结算返回营地。
- 将圆柱占位地块替换为 View 层生成的 pointy-top 六边形薄棱柱，带独立 MeshCollider、可探索/地块名称标签，并保持原地图坐标和 Adapter 接口不变。
- 资源点采集完成后通过 Hunt 回调立即刷新世界标记；同地块多个资源点全部耗尽后不再残留黄色交互球。
- 营地 HUD 增加年鉴视图，展示狩猎人数、损失、带回资源与 Timeline 条目。
- 营地 HUD 增加“发明与工坊”页，接通资源投入、发明解锁、配方开放、制造消耗与库存产出的长期成长闭环。
- 配置首个基础发明“工具”、加工台配方“打磨石器”与产物“石质工具”；内容均由 ScriptableObject/序列化目录驱动。
- 配置首个第二年营地叙事事件“拾荒者归来”，事件确认后获得蘑菇肉，并把年鉴状态从“将发生”更新为“已发生”。
- 在缺少角色 Prefab、相机装配和场景主光源时提供可游玩的 View 层降级表现；没有改变战斗数据层规则。
- 增加可配置的全屏启动菜单：检测存档后提供“继续战役/开始新战役”，覆盖旧战役前二次确认；继续游戏会跳过仅属于新战役的开场叙事。
- 发明与制造成功后立即保存，返回营地仍保留原有自动保存；存档 Adapter 以调用序号串行写入，避免快速连续操作被旧快照覆盖。
- 增加独立装备仓库与字符串化猎人负载存档：非资源产物不再丢失，旧存档会补齐空仓库与空负载，并由内容目录恢复 `ItemData` 运行时引用。
- 配置首件基础武器“粗制石刃”及其工坊配方，跑通“素材 → 石质工具 → 武器 → 装备猎人 → 卸下/死亡返还”的长期装备流程。
- 装备规则下沉到纯 GameCore：每名猎人最多携带 9 件装备、其中最多 2 把武器；营地 HUD 可查看装备仓库、为存活猎人装备，并在猎人卡片上卸下。
- 增加营地猎人到旧决战运行时的一次性 Combat Adapter：进入决战时投影姓名、力量、闪避、意志与第一武器，石刃速度成为命中尝试数、威力成为攻击力加值。
- 决战预备槽扩充到 4 个，与营地允许的 1—4 人出发规则一致；未出发槽会从 `PlayerCharacters`、Boss 选目标和棋子交互中排除并隐藏，开发面板无狩猎名单时仍回退原战斗配置。
- 旧存档恢复时一并重建非序列化 `Collectibles`，修复载入旧战役后单人进入狩猎会在状态栏空引用中断的阻断问题。
- `GameManager.CurrentPhase` 改为只读转发 `CombatTurnFlow` 的权威回合阶段，避免行动卡与效果条件永久误判为玩家回合；保留旧字段等待后续版本化清理。
- 决战攻击已支持从出战猎人的两把武器中选择本次使用项；选择会切换有效命中尝试数，武器射程会过滤不可用候选，选择 UI 明确展示威力、尝试、射程与精准。
- 配置第二把基础武器“筋腱投石索”及工坊配方：碎石与柔软器官经“工具”发明后可制造；其低威力、高尝试、三格射程与石刃形成首个可感知负载取舍。
- 新增 Playable 专用“谨慎推进”和“武器攻击”行动卡，并为 4 个出战槽配置同一套最小卡组；旧的空白行动卡资产保持不变，启动组合根改用新内容。
- 补齐可序列化的基础攻击效果数据，使攻击卡能通过现有 `CharacterActionCardInstance` 工厂生成真实 `CharacterAttackEffect`，不依赖 View 层特判。
- 新增 Playable Boss“无光兽”、可序列化的“黑暗撕咬”行动卡与 4 张命名受击部位；Boss 回合会实际选择存活出战猎人，完成闪避判定与躯干伤害。
- 在角色攻击管线末端增加幂等胜利判定：全部受击部位摧毁且结果表现完成后发布既有 `BossDefeatedEvent`，自动结算狩猎、发放击杀战利品并返回营地。
- 修正胜利事件订阅顺序造成的击杀掉落丢失：现在由阶段协调器在读取并清空战利品前显式累计击杀奖励；旧受击部位的空效果条目也会被安全跳过。
- 为 Playable 行动增加“准备选择 → 原子提交费用 → 执行状态变更”桥接契约；移动目标、武器选择与射程校验现在都在扣除时点前完成，取消或无合法武器不会消耗费用。
- “谨慎推进”改用可准备移动效果，“武器攻击”改用可准备攻击效果；旧行动效果继续沿用原执行路径，避免一次性改写既有内容体系。
- 接通决战伤亡与营地长期状态：进入战斗时恢复猎人四部位生命、护甲和可见死亡牌堆；受伤后把部位生命、死亡牌数量与永久损伤同步回营地存档模型。
- 新增战斗伤亡协调器：死亡结果确认后，阵亡者从战斗名册、棋盘与时间轴移除，装备返还营地仓库；若出战小队全灭则以失败记录结束本次狩猎，营地无人存活时沿用既有 GameOver 流程。
- 接通致命伤存活事件闭环：可序列化事件目录按权重选择内容，伤势结果确认后再展示独立事件，并通过既有 `EventEffect` 将效果施加到实际受伤猎人；首个基础事件“幸运儿”提供命运值奖励。
- 战斗结果弹窗会在长文本下自动缩放字号，确保事件叙事和效果摘要同时可见，不再裁掉玩家决策所需的结果信息。
- 接通猎人狩猎后成长闭环：存活参战者返营时年龄 `+1` 并获得 1 点待分配成长；营地猎人卡可把成长点投入胆识或知识，二者遵循正式上限 8，分配后立即保存。
- 成长规则下沉到纯 GameCore，Hunt→Settlement Adapter 只负责去重参战名单、发布成长事件并写回长期模型；旧存档缺少的新字段按 0 兼容。
- 按 Timeline 正式设计接通“每年多次狩猎”：年度狩猎配额由营地内容目录配置，默认每年 2 次；第一次返营只记录本年进度，达到配额后才推进年份、重置进度并调度新年度事件。
- 年度进度与配额进入存档，旧存档加载时由内容目录补齐并规范化；开发者跳年和 Timeline 强制跳年会清零跨年进度，避免配置变化后产生非法计数。
- 修复 Play Mode 脚本域重载后 `GameManager.Update` 连续访问已清空回合状态机造成的逐帧空引用；运行更新入口现在允许组合对象尚未重建的短暂窗口。
- 接通正式“鼓舞”意志行动：消耗 1 意志，选择一名处于加班状态的队友并恢复 1 时点；无合法目标或取消选择时会在费用提交前结束。
- 共享猎人行动卡改由 `BattleSetup.SharedHunterCards` 从组合根注入，避免逐份修改 4 个角色槽资产；“鼓舞”沿用现有准备、费用原子提交、执行和每回合重置契约。
- 补齐 `IPlayerInputProvider.RequestSelectTarget` 的可用 UGUI View，目标按钮显示实际猎人姓名并提供取消入口；旧 ID 接口通过可选名称解析器保持兼容。
- 接通三色战斗灵感思维区：红/蓝/黄灵感以独立 Token 和稳定 ID 建模，默认容量 4；满容量时由玩家明确替换已有灵感或丢弃新灵感。
- 新增共享行动卡“专注”：消耗 2 时点，使用现有掷骰 View 同时生成两枚三色结果，并逐枚写入思维区；结果文本与 3D 卡牌同步反馈颜色和容量。
- “谨慎推进”和“武器攻击”改为正式 `2 时点 + 1 任意战斗灵感` 费用；支付多个/指定颜色费用时先保留特定颜色，再由可选资源选择 View 选中确切 Token，提交后统一刷新思维区。
- 接通基础行动卡完整生命周期：正面卡左键执行、右键爆发并翻面，具备主动恢复的背面卡可左键支付费用恢复；背面卡在领域状态和解析入口都无法绕过 View 再次打出。
- “武器攻击”使用后翻面，左键支付 1 任意战斗灵感恢复，右键爆发返还 1 时点；“谨慎推进”使用后翻面，猎人回合结束自动恢复，右键爆发获得 1 蓝色灵感。
- 按正式怪物规则补齐 Boss 全局生命：每次有效伤害同时削减 1 点全局生命，部位耐久继续独立承担效果与掉落；全局生命归零成为正式胜利条件，旧上下文保留“全部部位摧毁”的兼容回退。无光兽配置为 6 点生命，决战 View 持续显示名称、数值与生命条，胜利领取状态由 Boss 生命对象保证全局幂等。
- 接通玩家操控怪物的目标选择流程：Boss 攻击效果可序列化声明玩家选择、最近、伤势最重或随机策略，GameCore 只计算优先候选，Playable Adapter 读取当前存活战斗快照并复用现有目标选择 View。取消必选目标会提示并从合法候选中随机回退，不能借关闭窗口跳过怪物攻击；同距或同伤势并列时仍交给玩家裁决。
- 接通正式工坊建设闭环：新增稳定 `WorkshopId`、可序列化工坊目录、GameCore 建造计划、Adapter 原子扣费与持久化设施状态；“工具”发明后可支付碎石与柔软器官建造“护甲工坊”，建成前韧膜胸甲配方保持锁定，建成后立即开放并保存。
- 新增独立工坊建设 View，沿用营地全屏输入遮罩与普通窗口模式；设施名称、说明、前置发明和材料均由 ScriptableObject 配置，不把内容数值写入界面或规则代码。
- 修复新导入 TurnBasedPack 在 Unity 6000.5 下因 `Object.GetInstanceID()` 强制废弃导致的编译错误；ActionQueue 调试窗口改用 `GetEntityId()`，未改动包的运行时队列语义。
- 新增通用 `IContentTableSource<TRecord>` 与 JSON 事件表 Adapter，支持以稳定 ID 向现有 ScriptableObject 内容注入或覆盖事件；非法选项、类型或效果会整行拒绝，不生成部分有效的残缺内容。物品、装备等大规模内容可复用同一表源边界，当前暂未迁移。
- 以 `events.json` 配置首个主线抉择“巨大的脸”：大胆对话使用胆识判定并可获得胆识，谨慎接触使用知识判定并可获得知识；事件在第一年进入主线年鉴。
- 固定主线改为会话内幂等调度：同一 Timeline 不重复呈现，未完成事件读档重建后恢复呈现，完成后永久停止触发，避免退出事件窗口导致主线丢失。
- 接通猎人退休闭环：将“存活”与“可出战”拆为正交状态；年龄达到 12 的猎人在再完成一次狩猎后退休，仍保留在名册和历史中，但退出组队、战斗、事件行动者、休养、装备与全员增益候选。
- 退休由 GameCore 判定、Adapter 编排、HunterManagement 原子提交：装备自动返还仓库，年鉴写入独立 `RosterChanged` 条目，名册事件刷新 View；全员退休不误判全灭，并可走既有免费紧急招募防止战役软锁。营地 HUD 会单独展示退休名单。
- 接通 Timeline 延时事件闭环：事件效果可以用稳定事件 ID 和延迟年数安排未来后果，GameCore 验证年份与溢出，Timeline 持久化年鉴预告、补触发错过年份的日程，并保证同会话与完成后不重复呈现；目标内容暂时缺失时保留日程等待恢复。
- 事件表新增 `Scheduled` 内容类别和引用校验，延时目标必须存在、ID 唯一且属于只调度类别；“巨大的脸”的任一结果都会预告两年后的“石脸的回声”，到期叙事给予基础碎石奖励。EventSystem 仅依赖窄 `IDelayedEventScheduler`，不直接耦合 Timeline 实现。
- 接通猎人死亡后果闭环：两条永久死亡入口统一由 HunterManagement 提交死亡状态、装备返还、`RosterChanged` 年鉴、幸存者激励与名册通知；死亡年鉴使用稳定猎人 ID 幂等去重，重复死亡通知不会重复返还装备或发放成长。
- “激励”暂以现有待分配成长点承载，并由内容目录配置每名幸存者获得量与死者最低年龄；当前基线为年龄至少 2、活跃幸存者各获得 1 点，退休者与年龄 1 的新兵不参与，避免最低成本的新兵献祭。营地提示改为延迟队列，战斗持续超过提示时长或连续多人死亡也不会在回营前过期。
- 接通致命伤存活后的永久损伤闭环：现有 `IPermanentInjuryResolver` 由 Unity 内容目录实现，按受伤部位加权抽取；领域状态以稳定 ID 幂等收录，Adapter 首次写入长期存档并一次性施加属性修正，读档会恢复到战斗伤势模型但不会重复扣属性。
- 当前提供四个可编辑基础内容：头部“一眼失明（技巧 -1）”、躯干“断裂肋骨（力量 -1）”、手臂“残损手臂（力量 -1）”、腿部“跛行（移动 -1）”。战斗结果沿用既有伤势窗口展示，回营猎人卡会持续显示永久损伤；启动配置要求四部位目录完整且稳定 ID 全局唯一。

## Unity MCP 验证证据

- 冷启动地图：37 格全部绑定有效 `HexTileData`，1 个起始地块、1 个 Boss 遭遇，地块池 4 类。
- 一次真实采集：浅水沼泽生成资源点，采集弹窗正常显示，3 名猎人参与，柔软器官由携带物转入营地，库存 `0 -> 1`。
- 一次真实遭遇：Boss 坐标 `(-2, 3)`，从起始地块连续翻开 3 次进入 `BossFight`。
- Boss 阶段完成一次结束回合并发布击败结算，返回 `Settlement`；Unity Console 为 0 Error。
- 新增纯 GameCore EditMode 测试程序集，首批资源规则用例 Unity MCP 实测 `3/3 Passed`。
- 补充出发人数边界后，Unity MCP EditMode 合计 `6/6 Passed`。
- 补充年度可用区间与事件资源效果测试；当前 Unity MCP EditMode 合计 `9/9 Passed`。
- 补充发明前置、成本、工坊解锁、材料聚合与异常数量测试；当前 Unity MCP EditMode 合计 `15/15 Passed`。
- 营地正式出发回归：空队伍被拒绝，单独选择斥候后 Hunt 活跃猎人为 1，撤退返回营地并写入 1 条狩猎史。
- 资源反馈回归：雕像平原的 2 个资源点采集前有 1 个世界标记，全部耗尽后地块标记与全场资源标记均为 0。
- 事件回归：首次撤退进入第 2 年并展示“拾荒者归来”；确认后蘑菇肉 `1 -> 2`，对应 Timeline 条目 `IsCompleted = true`。
- 六边形地图回归：37/37 格均为 14 顶点、72 索引的六边形 Mesh，37/37 绑定 MeshCollider 与点击组件；垂直射线 36/37 直接命中地块，起始格由小队胶囊优先命中。
- 六边形玩法回归：翻开 `(-1, 1)` 后标签更新为“雕像平原”，2 个资源点耗尽后标记立即消失；继续翻牌后 Boss `(-2, 0)` 正常进入 `BossFight`。
- 营地成长回归：开局碎石 `2`，解锁“工具”后为 `1`，制造“石质工具”后碎石 `0`、石质工具 `1`；配方在发明前保持锁定。
- 序列化回归：将制造后营地数据转为 JSON 并重新注入，石质工具数量与“工具”解锁状态保留，内容目录重新绑定为 1 个发明、1 个配方。
- 配置攻击回归：重复材料成本会按资源名汇总，负数材料、负数发明成本与零产出配方均被规则层拒绝。

- 里程碑玩家反馈：营地猎人卡现直接展示特性与症状；达成里程碑时显示可排队的非阻塞提示，批量补领不会覆盖上一条消息。Unity MCP 用真实目录验证双属性 8 的猎人首次获得 6 项、再次同步 0 项，JSON 往返保留 6 个 ID；逐点分配 `胆识 1 → 2` 和事件一次增加到 2 均立即领取。数据结果为 `first=6 / second=0 / traits=6 / claimed=6 / willpower=3/3 / strength=2 / accuracy=2 / evasion=2`，聚焦 EditMode 测试 `4/4 Passed`，未使用截图。

## 已发现的设计问题与重构方向（暂不执行）

1. `GameManager` 同时负责阶段、UI、存档、战斗装配和结算，职责过重。后续拆为阶段协调器，并由组合根注入各阶段服务。
2. `PlayableHuntContentRuntime` 是为保持旧构造器签名而增加的静态桥接。后续应由 `HuntSessionFactory` 显式注入内容目录、随机源和事件池。
   `PlayableSettlementContentRuntime` 也承担相同的旧接口兼容职责，后续应一并迁入组合根工厂。
3. `GameCameraManager` 的场景引用缺少公共配置入口。本轮使用阶段相机适配器；后续统一为 `IPhaseView.Configure`。
4. `ModuleSystem` 通过接口名推导实现名，`IUpdateDriver` 与原实现名称不一致会导致模块发现失败。建议改为显式注册或类型属性映射。
5. Hunt UI 使用静态事件总线，原兼容门面会在显式取消订阅后再次统一清理，退出 Play Mode 时触发 TEngine 重复删除异常。本轮已将门面清理改为幂等；后续仍应引入按阶段或对象所有权管理的订阅作用域。
6. 资源点标记现通过 Hunt 回调即时刷新，已消除耗尽后残留；但回调仍是单委托字段，后续应替换为可多订阅、带生命周期作用域的领域事件。
7. 采集翻牌目前只表现最终总数量，未逐张显示命中/落空；应让领域层返回逐卡结果供 View 呈现。
8. 战斗缺少正式 `CombatFieldRulesSO` 和角色 Prefab 时会使用基础规则与几何占位，适合流程验证但不是最终内容品质。
9. 地图已改为运行时生成的六边形 Mesh，适合无美术资源时的流程版本；正式制作应改用可配置 Prefab、共享材质和贴图，同时保留当前 View 工厂接口。
10. 本轮已补充资源规则的独立 EditMode 测试程序集；地图生成、资源转移和跨阶段生命周期仍需要 PlayMode 集成测试。
11. `DepartureRules` 当前只校验数量，不校验 ID 是否属于存活猎人或是否重复。新 HUD 只提交存活猎人的去重 ID，因此玩家路径安全；后续应把 roster 校验下沉到领域规则。
12. 可游玩营地 HUD 使用 IMGUI 作为无场景 Prefab 时的组合根降级 View。正式 UI 资源齐备后，应保留相同命令接口并替换为预制 UGUI/UI Toolkit View。
13. `TimelineSystem.GetEventsForYear` 会为随机/营地事件创建 `AnnalEntry`，但固定年份的主线事件目前只进入触发列表，没有同步创建年鉴条目。当前内容未配置主线事件；后续应统一由 Timeline 记录所有事件来源。
14. `InventionSystem.ApplyEffect` 仍通过 `effectDescription` 文本匹配效果。当前“工具”只承担解锁条件，不受影响；后续应改为可序列化的效果策略列表，文本仅用于展示。
15. 正式启动菜单已提供新游戏/继续游戏，加载后会重新注入营地数据；但存档尚无 schema 版本与迁移器，未来调整 `SettlementInstance` 字段时需要增加版本化迁移流程。
16. 工坊装备产物、装备仓库、猎人负载存档及双武器选择已通过独立 Combat Adapter 接通；`range` 已参与合法武器过滤，`accuracy` 与 `specialRule` 也已进入只读投影契约。但旧战斗采用确定性的力量/韧性比较，没有正式命中牌池，暂不能让精准参与结算；后续应在正式牌池规则落地时消费该契约，而不是把精准临时换算成伤害或速度。
17. 存档写入现已解决进程内竞态，但仍直接覆盖目标 JSON。若进程在写盘中断，文件可能损坏；正式发布前应改为临时文件写入、校验后原子替换，并保留最近一份可恢复备份。
18. `HunterState.EquipmentIds` 是旧的实例 ID 存档字段，目前没有全局实例注册表；新流程使用稳定的 `EquippedItemNames`。后续版本化迁移后应移除旧字段，或改为稳定内容 GUID，避免两套负载表示长期并存。
19. `HunterData.startingEquipment` 已进入内容注册表，但新战役还没有应用模板初始装备，也没有编辑器侧的 9 格/2 武器校验。当前三名初始猎人均为空负载，不影响可玩流程；配置初始职业装备前应统一复用 `EquipmentRules` 完成校验与装配。
20. 战斗棋盘、行动卡和角色槽仍在 `GameManager.Awake` 中提前按占位 `CharacterConfigSO` 构建。本轮 Adapter 能正确投影并过滤 1—4 人名单，但 Boss、地图和行动卡尚不是按实际遭遇动态生成。后续应把构建时点迁到 `CombatSessionFactory`，由 Hunt 遭遇显式提交 `BattleSetup`。
21. `Equipment`、`Collectibles` 等运行态集合使用 `[NonSerialized]`，旧存档反序列化后可能为 `null`。本轮在内容恢复边界补齐并为状态 View 增加空值降级；后续应建立统一 `SettlementSaveMigrator.RehydrateRuntimeState`，避免每新增运行态字段都分散修补。
22. `GameManager` 原有 `_currentPhase` 从未随 `TurnStateMachine` 更新，本轮已让公共接口读取 `CombatTurnFlow` 权威状态；后续移除旧字段，并让 `TurnPhaseChangedEvent` 直接携带领域层的 `TurnPhaseChange`，消除重复状态表示。
23. 行动卡 `TargetingRuleData` 与武器射程目前分别门控：前者限制卡牌形状，后者过滤武器距离，实际效果为交集。该行为符合当前流程，但尚无统一的目标预览契约；后续应由 `AttackTargetingPolicy` 合成两者，使棋盘高亮与最终可执行性始终使用同一结果。
24. Playable 移动与攻击已通过可选的准备效果契约解决“先扣费、后取消”；但旧行动效果仍可能在费用提交后执行异步选择。后续应把 `Prepare / Commit / Execute` 正式下沉到通用 GameCore 行动事务，并逐步迁移旧效果，而不是长期保留 Playable 专用桥接。
25. 旧 Boss 行动卡与受击部位资产大多为空内容，部分受击部位还带有空效果条目。本轮 Playable 内容已完全绕开空资产，并在解析边界增加空值保护；后续若保留旧内容，应增加编辑器资产校验器，在保存时拒绝空名称、空效果和非法韧性/HP。
26. 击杀战利品原本依赖 `BossDefeatedEvent` 的订阅顺序，阶段协调器可能先清空奖励。本轮改为结算入口显式调用 `AccumulateDefeatLoot`；长期应让战斗领域返回不可变 `CombatOutcome`（胜负、掉落、伤亡），由阶段协调器一次性消费，彻底移除顺序敏感的共享事件副作用。
27. 权威 `TimelineManager` 提交时点后，`CharacterRuntimeData.CurrentTimePoints` 要等事件消费才同步；异步攻击尚未结束时两者会短暂不一致。玩家最终显示正确，但条件判断若混用两个来源会产生时序隐患；后续应让角色状态接口直接投影时间轴，或明确区分权威写模型与延迟读模型。
28. 正式猎人文档写明躯干生命为 `3`，现有 `HunterHitPoints` 与 `HunterInjuryProfile.CreateDefault` 都使用 `4`。本轮保持现有存档和战斗数值兼容；数值定稿后应统一数据资产与领域默认值，并提供存档迁移。
29. `HunterState.IsDead` 仍把头部或躯干生命归零直接解释为死亡，但正式规则要求“归零后再次受伤并抽到死亡牌”才永久死亡。当前可游玩流程以 `IsAlive` 和 `HunterInjuryState.IsDead` 为权威，不受该属性影响；后续应删除该派生属性或改名为 `HasCriticalBodyPart`，避免新代码误用。
30. `EventSystem.ApplyEffect(effect, target)` 原先对命运、意志与疯狂效果忽略显式 `target`，只读取内部 `_selectedHunter`，使战斗上下文事件可能奖励错误对象或空对象。本轮以显式目标优先、内部选择为兼容回退修复；后续应改为不可变 `EventResolutionContext`，移除有状态的隐式目标与队列耦合。
31. 存活事件暂时复用通用 `EventData`，但 `EventCategory` 没有 Survival 分类，且通用 `EventSystem` 对未支持效果只记录警告。当前由显式 `PlayableSurvivalEventCatalog` 限定内容范围；后续应增加存活事件分类和资产校验器，在编辑器保存时拒绝空内容、非正权重及不支持的效果类型。
32. 正式猎人成长设计规定年龄超过上限后退休，但尚未定义退休猎人是否留在名册、能否参与营地设施、装备如何处理以及传承入口。本轮在 12 岁封顶并停止继续获得成长，避免把退休错误实现成死亡；规则明确后应新增独立 `HunterAvailabilityState`，不要复用 `IsAlive`。
33. 年龄 2、5、8 的固定奖励或事件尚未提供具体内容。本轮规则会通过 `HunterAdvancedEvent.ReachedMilestone` 暴露准确触发点，但不硬编码奖励；后续由可序列化成长里程碑目录消费该事件，并把结果写入 Timeline。
34. 年度狩猎配额的设计值来自内容目录，但当前运行时也把该值写入存档用于 HUD 与离线检查；加载时内容目录会覆盖存档值并规范化进度。长期应把“战役规则配置”与“战役进度状态”分离：存档只保存当前完成次数和规则集版本，配额始终由版本化 CampaignRules 提供。
35. `TimelineSystem.AdvanceYear(HuntRecord)` 现在承担“记录狩猎并按配额决定是否推进年份”，旧方法名已经不能准确表达语义。为避免扩大已有接口改动本轮保留名称；后续应迁移为 `RecordHunt` 并返回显式 `CampaignTimeOutcome`，让阶段协调器区分“返营”和“跨年”。
36. Unity 编辑器在 Play Mode 中脚本域重载时不会自动重建 `GameManager` 的纯 C# 运行图；本轮用更新入口空值保护消除异常风暴，但热重载后的进行中战斗不能保证无缝继续。长期应把运行图构建提取为幂等 `InitializeRuntimeGraph`，由 `Awake/OnEnable` 和域重载恢复入口共同调用。
37. `TimelineService.Register` 创建角色时 `Limit` 为 0，必须等首次 `ProcessOverflowForNewPlayerTurn` 才获得本回合上限；若初始化完成前有系统累计时点，溢出债务会被错误放大。当前正常回合入口会先处理溢出，玩家路径安全；后续应让注册显式接收初始上限，或新增不可跳过的 `BeginPlayerTurn` 领域命令。
38. `IPlayerInputProvider.RequestSelectTarget` 只传整数 ID，View 无法自行获得姓名、阵营和状态。本轮以组合根注入的名称解析器补齐玩家可读标签；长期应改为只读 `TargetOption` 列表，让选择条件和展示信息来自同一快照。
39. 行动卡事务在目标选择后提交费用，再执行效果；若未来引入并发反应或网络同步，目标可能在两阶段之间失效而费用已经扣除。当前单线程行动队列内没有并发变更窗口；长期应让提交阶段同时验证准备令牌，或为失败效果提供领域级补偿事务。
40. `CharacterRuntimeData.CombatInspiration` 仍是旧的聚合整数，而新权威模型是按颜色与 ID 区分的 `CombatInspirationMind`。本轮仅在既有同步边界投影数量；需要持久化跨战斗灵感时，应版本化保存 Token 列表，不能继续从整数反推颜色。
41. 思维区容量目前采用领域默认值 4，尚未进入猎人模板、装备或成长配置。当前符合基础规则；后续应由版本化角色能力目录提供容量修正，并在缩容时返回需要玩家处理的显式结果。
42. “专注”复用了通用离散结果掷骰窗口，已完整表达九种颜色组合，但没有实体三色骰的动画与逐骰停靠表现。View 层可在不改变 `FocusInspirationRules` 的前提下替换为专用骰子表现。
43. `CharacterEntity` 的降级 Prefab 原本没有思维区引用，本轮在 View 初始化时按接口补建可用网格；正式角色 Prefab 完成后应在 Inspector 配置独立思维区锚点和布局，并保留运行时补建作为缺失资源保护。
44. 旧 `IFlipCondition` 的 `Evaluate/Consume` 都是同步接口，无法表达“先异步选择资源、再原子提交”的主动恢复费用。本轮以可选 `IPreparedActionCardRestoreCost` 让 Playable Adapter 复用行动费用事务；长期应把 `Prepare / Commit` 正式纳入通用恢复条件契约。
45. `PlayerTurnState` 只检查已经选中某个猎人，没有在命令边界再次验证卡牌 Owner 就是当前选中猎人。当前 3D View 只展示选中猎人的面板，正常玩家路径无法越权；未来接入网络或快捷键命令前应把 `selectedCharacterId` 纳入卡牌命令校验。
46. 3D 卡牌右键爆发暂时沿用项目现有 `OnMouseOver + Input.GetMouseButtonDown` 输入方式。它适合当前桌面鼠标版本；后续需要手柄、触屏或多人输入时，应由语义化 `CardInteractionAction` 适配到同一命令接口。
47. `BurstRewardData.currencyReward` 会随 `DiscardResult` 返回，但 `GameManager` 当前只结算 `timePointReward`，没有权威战斗货币容器。本轮基础卡没有配置货币奖励；引入相关内容前应先定义资源归属和结算 Adapter，避免配置存在但奖励静默丢失。
48. 设计文档要求“先抽取整批结果，再分配至受击部位”，而旧数据只有部位韧性。本轮已增加 Boss 全局基础韧性并迁移为批量结果分配；仍需在规则定稿时明确部位韧性是结果分配后的修正、仅用于暴击，还是应从资产中移除。
49. 正式攻击牌堆规则尚未定义暴击。本轮只在抽到成功牌后兼容旧的“总攻击力至少两倍韧性”阈值，避免现有暴击效果失效；数值规则定稿后应把暴击作为牌面、额外抽取或独立领域规则，不再依赖旧确定性检查。
50. `WeaponData.strengthBonus` 在旧流程表示力量加值，在新设计语义中承担“武器威力抵消韧性”的职责。当前 Adapter 显示与计算已统一按威力使用；长期应增加版本化 `Power` 字段并迁移资产，避免名称误导内容设计者。
51. 当前 View 用均匀随机索引等价模拟洗牌后抽一张，没有为每张成功/失败牌创建场景对象。这保证概率、测试与流程正确；正式表现可在 `IAttackResultDeckInputProvider` 后增加洗牌、展开和翻牌动画，无需修改领域规则或攻击步骤。
52. `战斗系统 Combat system.md` 的怪物攻击段落写“攻击次数张命中卡”，而更具体的 `怪物 Monster.md` 写“怪物精准张命中卡”，且行动卡属性明确区分精准与次数。本轮采用后者：精准决定牌堆构成、次数决定独立抽取次数；应回写正式文档消除冲突。
53. `CombatRules.IsBossAttackDodged` 仍保留旧的百分骰阈值算法，现已不在正式 Boss 攻击管线中使用。为避免扩大已有接口修改，本轮不删除；待旧战斗兼容层确认无调用后应移除，并由静态架构测试禁止重新引用。
54. 多次 Boss 攻击目前复用同一目标与身体部位，符合当前“黑暗撕咬”基础卡，但尚未表达“每次命中分别指定受击部位”的完整规则。后续应让 Boss 行动效果提供部位选择策略或结果序列，而不是在通用管线中硬编码随机部位。
55. Boss 命中牌堆和猎人攻击结果牌堆各自拥有二元牌堆值对象，暂不抽象成通用泛型牌堆，以保留领域语义与不同的零值规则。若后续出现第三种同构临时牌堆，再提取共享的加权抽取内核，避免过早抽象。
56. 正式文档没有说明攻击次数大于临时结果牌堆总数时如何处理。本轮在牌堆耗尽后重洗同构牌堆继续抽取，保证武器速度不会静默丢失；数值定稿后应明确这是正式规则，或约束牌堆规模始终不少于攻击次数。
57. `HitLocationCardData.toughness` 仍存在于旧资产，批量攻击的成功率已改由 Boss 全局韧性决定；它目前只间接参与未定稿的旧暴击阈值。本轮已从玩家界面隐藏该误导数字；后续应将字段明确改名为“部位暴击阈值/韧性修正”，或完成资产迁移后移除。
58. `IAttackResultDeckInputProvider` 是上一版逐部位随机抽取的兼容接口，正式批量流程现使用 `IAttackResultBatchInputProvider`。确认没有外部扩展依赖后应删除旧接口及单抽 UI，避免两条输入协议长期并存。
59. 批量结果在攻击开始时一次性生成，随后逐张揭示和分配，因此中途部位效果不会回写剩余牌堆。当前内容没有改变力量、武器威力或 Boss 韧性的部位效果；未来增加这类效果前需要明确攻击属性采用行动开始快照还是逐结果实时重算。
60. `武器熟练度.md` 写“第一武器格为空则不获得”，而完整猎人文档明确“未携带武器时默认拳头并获得拳熟练度”。本轮采用后者以保证空手玩法成长；正式文档应统一唯一规则来源。
61. 现有 `HunterState.WeaponProficiency` 只有单一整数，无法长期区分刃、弓、拳等武器类别。本轮先接通有效伤害、胜利结算、玩家反馈和存档闭环，并以武器名称作为资格键；后续应增加稳定的武器类别 ID 与可序列化熟练度条目列表，再通过存档迁移保留旧总值。
62. 当前熟练度只在 Boss 胜利时结算。现有流程没有“Boss 战主动撤退但猎人存活”的正式入口；若未来允许决战撤退，应让不可变 `CombatOutcome` 同时携带本场有效武器记录，并在所有战斗结束分支统一结算。
63. `PlayableWeaponMasteryTracker` 复用 Combat Adapter 的存活猎人与角色顺序建立映射，与当前 `PlayableHunterCombatAdapter.Apply` 一致，但仍隐含依赖同一排序约定。后续 `CombatRosterBindingResult` 应返回显式 `CharacterId → HunterId` 绑定表，让伤亡、熟练度及其他长期成长共用稳定身份映射。
64. 年度事件防重复目前只比较最近一条随机年鉴记录，属于“避免连续重复”而不是完整的不放回事件袋。事件数量继续增长后，应由战役存档维护近期事件窗口或可重置牌堆，避免三张事件长期交替仍显机械。
65. Playable 路径已由独立事件 View 和显式事务替换 `PlayableSettlementHud` 的直接结算，正式判定不会二次掷骰；但旧场景若仍挂载 `EventPopup`，其“展示一次、确认时再调用 `ResolveChoice`”的兼容路径仍可能二次掷骰。确认旧场景依赖后应迁移或删除该入口，让所有 View 共用同一事务。
66. 年鉴目前只记录事件名称与是否完成，不记录玩家选择了哪个选项及具体结果。当前结果会即时显示且资源状态正确；后续应追加结构化 `EventOutcomeRecord`，让年鉴真正保存营地故事，而不是仅保存事件标题。
67. `CheckType.Custom` 已存在于数据枚举，但事件资产没有可配置的自定义属性键或加值提供者，当前会按 0 加值处理。后续应增加稳定属性 ID 和 `IEventCheckBonusProvider`，并让资产校验器拒绝缺少属性配置的 Custom 判定。
68. `EventOption.alwaysAvailable` 只有布尔标记，没有与之对应的资源、猎人状态或前置事件条件模型，View 无法解释“非永久可用”的判定依据。后续应新增可序列化条件列表并由 GameCore 返回不可用原因，避免把可用性逻辑散落在界面。
69. 本轮为防止事件结果在玩家立即退出时丢失，由 Playable Event View 在提交后调用存档入口；这保证当前玩家路径安全，但让 View 暂时知道持久化策略。后续应发布不可变 `SettlementEventOutcomeCommitted`，由阶段协调器统一存档，旧 EventPopup、自动事件和未来非 UI 入口也应消费同一提交边界。
70. `PlayableEventChoiceTransaction` 目前以 `partial EventSystem` 方式封装旧系统的隐式选中猎人、完成记录和事件链队列，属于低侵入兼容层。长期应提取无状态 `IEventResolutionSession`，显式持有事件、选项、行动者、随机源和链结果，再让旧 `EventSystem` 仅承担 Adapter 职责。
71. 招募速率、人口上限和成本在设计文档中仍是待平衡项。本轮将其全部放入内容目录，当前值 `每年 1 名 / 存活上限 6 / 蘑菇肉 1` 只承担流程基线；数值测试后应调整资产，不要把平衡值下沉进规则代码。
72. 全员阵亡时允许免费援助且绕过本年次数限制，这是防止战役永久死档的明确降级规则；玩家若刻意连续牺牲最后一名猎人可以反复触发。正式失败压力落地后，应让紧急援助同时附加债务、灾厄进度或弱势模板，而不是简单删除防死档入口。
73. 招募年鉴目前只记录“名字加入营地”，尚未保存设计文档设想的身份信息、承诺或猎杀目标。后续应把 `RecruitmentOutcome` 扩展为结构化背景与承诺，并让相关 Boss/事件条件读取稳定 ID，而不是解析展示文本。
74. 正式招募路径已通过 `HunterIdentityRules` 避免读档后的 ID 冲突，但 `HunterInstance` 仍保留自己的静态 `_nextId` 降级构造路径。当前组合根与招募 Adapter 都显式传入 ID；长期应让实例构造只接受由 `IHunterIdentityAllocator` 分配的身份，彻底移除双重编号来源。
75. `LastRecruitmentYear` 是满足当前“每年一次”基线的单值存档字段，无法表达多个招募设施、事件赠送名额或跨年积攒次数。出现第二种正式招募来源时，应迁移为按来源记录的 `RecruitmentLedger`，避免继续堆叠布尔量和年份字段。
76. 营火休养的成本、恢复量与治疗次数仍是流程基线，当前通过内容目录配置为每次消耗 1 蘑菇肉并恢复 1 HP，未额外限制年度次数。正式数值测试后应调整资产或增加可配置的休养容量，不要把平衡约束硬编码进恢复规则。
77. 基础休养只处理身体部位的普通 HP，不移除永久伤势、症状或其他长期负面状态。这是为了保留正式医馆的职责边界；医馆落地时应以独立治疗方案与药品事务消费这些状态，而不是扩大 `HunterRecoveryRules` 的语义。
78. 启动菜单、年度事件和新增营地窗口尚未共用统一的 Overlay 协调器；Unity 同一帧只允许一个 `GUI.ModalWindow`，曾导致模态冲突和 GUILayout 失配。本轮新招募与休养窗口使用全屏输入遮罩加普通 `GUI.Window` 消除冲突；长期应由 `IOverlayCoordinator` 统一仲裁显示优先级、输入焦点和关闭顺序。
79. Recovery Adapter 的资源扣除尚未发布统一的资源或营地事务事件，当前 HUD 每帧直接读取状态所以显示正确。后续应返回不可变 `SettlementRecoveryOutcome` 并发布统一经济事件，使音效、提示、任务和其他观察者不依赖轮询或 View 私有反馈。
80. 休养成功后由 View 直接调用存档入口，能避免玩家立即退出导致进度丢失，但与事件提交处的问题相同，让 View 知道了持久化策略。后续应发布 `SettlementRecoveryCommitted`，由阶段协调器统一负责保存、年鉴和跨系统副作用。
81. 目的地当前能权威切换狩猎地图和资源分布，但 Boss 仍来自启动时构建的单一 `BattleSetup`。`GameManager` 只支持在 `Awake` 前注入战斗载荷，狩猎中遇敌无法安全重建棋盘；后续应让不可变 `HuntPlan` 同时携带地区、地图内容和 Boss 配置，并由 `CombatSessionFactory` 在遭遇时创建本场决战。
82. 当前存档只允许在营地继续，因此目的地作为单次会话状态不写盘仍然安全；如果未来支持狩猎中途保存，必须在存档中记录稳定的目的地 ID、地图种子与已翻开状态，不能依赖 `PlayableHuntDestinationRuntime` 的静态选择。
83. 可游玩 HUD 的出发按钮已统一经过目的地选择，但旧 `SettlementTable3D → SettlementUIManager` 的确认入口仍可直接调用 `SettlementManager.TryDepart`，从而绕过路线选择。正式替换旧营地 UI 前，应把“组队 + 目的地”合并为唯一 `PrepareHuntPlan / CommitDeparture` 命令，而不是继续在 View 层拦截。
84. 目的地目录支持最早开放年份，但当前 View 只展示本年可用路线；未来加入锁定地区后，玩家看不到解锁目标。届时应展示禁用的路线卡与 GameCore 返回的明确原因，同时确保至少一个基础地区始终可用。
85. `resourceHint` 与 `dangerHint` 是便于快速制作内容的展示文本，并不从地块池、资源权重或 Boss 难度自动推导；内容资产调整后可能出现描述漂移。正式内容管线应增加编辑器校验或结构化标签，让提示与实际生成规则使用同一数据来源。
86. `SettlementEventPresented` 实际同时承载营地和狩猎事件，命名与职责已经漂移。后续应引入 `IGameEventPresentationRouter`，按阶段把领域事件路由给对应 View，并移除 View 自行判断阶段的知识。
87. 旧 `EventPopupHunt` 仍会被实例化，但没有接入当前事件发布链，属于无效兼容 UI。确认旧场景不再依赖后应删除，避免后续误以为存在两套可用的狩猎事件实现。
88. 狩猎事件奖励目前直接修改营地资源库存，没有进入本场携带物；这意味着奖励不会随狩猎失败而损失。正式数值设计需明确事件奖励是否承担返程风险，再统一路由至 `HuntOutcome` 或携带物集合。
89. 同一地块可能分别进行一次“翻开事件”与一次“首次踏入事件”概率检查，当前沿用旧配置的 30% 与 15%，但节奏意图没有文档化。后续应把两类概率移入目的地配置并做整场事件密度测试。
90. 已检查移动事件的地块集合只存在于当前 Hunt 会话内。如果未来支持狩猎中途存档，需要连同地图种子、翻开状态一起持久化，否则读档后可重复触发或规避事件。
91. 狩猎事件是否立即存档目前由 View 根据阶段决定，虽能避免中途把未返营收益写盘，但持久化策略不应属于表现层。后续应让阶段协调器消费不可变事件结果，并在回营结算时统一提交长期状态。
92. `KillHunter`、`TriggerCombat`、`AdvanceYear` 等事件效果对狩猎阶段仍不完整或缺少明确语义；本轮内容刻意不使用这些效果。新增此类资产前应由事件效果策略与阶段协调器显式支持，不能仅靠 View 分支补丁。
93. 当前死亡牌堆只建模普通存活牌与死亡牌，设计文档中的“生存卡”尚没有独立牌面、动态入池来源和专属事件直结算。后续应把 `DeathCardType` 扩展为稳定内容 ID 驱动的牌定义，而不是继续为每种特殊卡增加枚举分支。
94. 致命伤预判与正式伤害结算会各调用一次 `IArmorMitigationRule`。现有平坦护甲规则是纯函数，因此结果稳定；未来若护甲规则消耗耐久、随机数或其他状态，应改为一次性生成不可变 `HunterDamagePlan`，再在玩家翻牌后提交，避免预览与结算不一致。
95. 当前死亡抽牌使用功能完整的 UGUI 背面按钮，已经保留公开、洗牌、选择和翻牌节奏，但还不是设计目标中的桌面 3D 卡牌演出。正式美术阶段应让同一 `IDeathDeckInputProvider` 由 3D 卡组 View 实现，并保持 GameCore 洗牌会话不变。
96. 旧存档中的 `SurvivalCards / DeathCards` 没有版本化上限校验；异常或手工破坏的超大数值会在进入战斗时创建同规模列表。统一 Save Migrator 落地时应校验死亡牌堆计数，并把无法恢复的组合降级为基础 1 张存活牌。
97. 资源采集命中率仍由 `ResourceSystem` 的统一默认值 `0.6` 提供，无法按资源类型、地区或工具配置。后续应把命中率或采集档案加入可序列化资源点配置，由 Adapter 读取并交给 GameCore，避免在 View 或规则中分散平衡参数。
98. `HarvestDrawPlan.MaximumCardCount = 32` 是抵御异常资产导致大量对象与随机调用的技术上限，但内容管线尚不会提示被静默钳制。后续应增加资源资产编辑器校验，并让 View 与领域规则共同读取已验证的卡牌数量。
99. 当前逐卡采集使用功能完整的 UGUI 卡牌，尚未达到桌面 3D 卡组的最终演出。正式美术阶段可让 3D View 消费同一不可变计划与事务揭示接口，不应把结算或随机逻辑重新放入卡牌动画。
100. 正常玩家输入会被守卫锁定，但外部阶段切换或场景卸载仍可能在部分牌已揭示时直接禁用采集 View，留下仅存在于旧 Hunt 会话中的待提交预订。后续阶段协调器应在卸载 Hunt 根节点前统一中止未开始事务，或显式完成/废弃已开始的覆盖层会话。
101. 正式案例把护甲制造放在需要建造的“护甲工坊”，当前营地模型只有发明与统一加工台，没有独立设施的建造、等级和可用状态。本轮先以“工具”发明解锁基础胸甲配方保证成长闭环；后续应增加稳定 WorkshopId 与设施状态，再让配方声明所属工坊，而不是按 UI 分组硬编码。
102. 正式设计尚未确定怪物攻击中护甲的精确处理方式。本轮沿用现有 `FlatArmorMitigationRule`，即护甲值直接抵消等量伤害；规则定稿后应替换注入的 `IArmorMitigationRule`，不需要迁移物品或 View。
103. 当前防具覆盖部位由 `ArmorStats` 中大于零的数值推导，足以表达基础分部位护甲，但无法表达“占用部位却不提供基础护甲”的特殊装备。出现这类内容前应给 ItemData 增加显式覆盖掩码或稳定槽位 ID，并进行资产迁移，不能用虚假 `+1` 数值占位。
104. 多个营地内容扩展若声明同名物品或同名配方，当前为保证可游玩会按资源名排序后保留第一个定义。正式内容规模增长前应增加编辑器校验器，把重复稳定名称作为构建错误，并逐步改用不随显示文本变化的内容 ID。
105. 当前只用 EditMode 内容测试保证“无光兽全局生命不超过所有部位总耐久”，可防止全部目标先被摧毁但 Boss 仍有生命的软锁；新增 Boss 资产前应增加通用编辑器校验器，并在内容导入或构建时直接报告非法组合。
106. `BossRuntimeData.MaxHealth` 的兼容 setter 会重建生命状态，若在战斗中被错误调用会同时回满生命并重置胜利领取状态。当前仅由 `BattleGenerator` 在会话装配时赋值；长期应改为构造参数或只允许 `CombatSessionFactory` 初始化，运行期接口只暴露只读生命。
107. 正式全局生命已由独立 View 显示，但仍是 IMGUI 顶置面板而非桌面上的 3D 怪物生命组件。美术与 Prefab 完成后应让新 View 消费同一 `IBossVitalityState`，无需把表现引用写回 GameCore 或 Adapter。
108. 不提供 `IBossVitalityState` 的旧战斗上下文仍以“全部部位摧毁”判胜，意味着迁移期存在两套胜利语义。待旧 BattleSetup 全部补齐生命配置后，应删除兼容重载，并以架构测试禁止创建无全局生命的 Boss 会话。
109. `IGameContext.PlayerCharacters` 只暴露基础角色状态，没有只读伤势快照；“伤势最重”策略当前由 Playable Adapter 从 `GameManager` 取得 `CharacterCombatStats`。后续应增加窄的 `ICombatRosterSnapshot`，让目标规则不依赖具体组合根，也便于 AI 预览与战斗回放。
110. `IBoardQuery.GetEntityPosition` 对不在棋盘上的实体返回零坐标，无法区分“真的位于原点”和“尚未放置”。当前决战存活名册都会被装配到棋盘；支持增援、离场或召唤后，应增加 `TryGetEntityPosition`，避免最近目标策略错误锁定离场单位。
111. 通用 `RequestSelectTarget` 协议固定提供取消入口，而 Boss 必选目标只允许取消后随机回退。长期应让请求携带 `SelectionRequirement` 与取消后果，由 View 直接展示“随机决定”而非语义模糊的“取消”，并让移动、鼓舞和怪物攻击复用同一明确契约。
112. `PlayableBossAttackEffectData.actionName` 与父行动卡的 `actionName` 需要在资产中重复配置，存在改名后提示文本漂移的风险。当前内容测试会验证实际卡与效果工厂；通用方案应让 `BossController` 在创建效果时传入只读卡牌执行上下文，而不是让效果反向查找父资产。
113. 第 101 项缺失的基础设施状态与配方门控已经落地，但 `CraftRecipe.requiredWorkshopId` 和工坊目录仍通过手工填写的字符串建立关联。当前内容测试会拦截基础护甲断链；内容规模增长后应增加通用资产校验器，或改为稳定工坊资产引用再在 Adapter 边界投影为 ID。
114. `BuiltWorkshops` 当前只保存布尔建成状态，尚不能表达设计文档中的设施等级、建设耗时、幸存者岗位与产能。规则明确后应迁移为版本化 `WorkshopState` 列表，并让建造、升级与人员分配分别使用显式命令，不要继续向布尔表旁追加平行字段。
115. 工坊建成后仍由 View 直接调用存档入口，和事件、招募、休养存在相同的持久化策略泄漏。后续应发布统一的 `SettlementTransactionCommitted`，由阶段协调器负责存档、年鉴和反馈，确保未来非 UI 建造入口不会漏存。
116. 工坊目录目前由 View 通过固定 Resources 路径加载，以避免扩大既有 `PlayableBootstrapSettings` 与场景资产改动。后续组合根应显式注入 `PlayableWorkshopCatalog`，并由启动配置校验其存在；View 只消费只读目录接口，不应长期承担内容发现职责。
117. 当前建造在材料提交后立即完成，没有实现设计文档尚未定稿的建设时间和幸存者参与要求。这是保证流程可玩的基础规则；相关数值明确后应增加可持久化建设队列与完成事件，而不是在 View 中延迟按钮或用协程模拟长期进度。
118. 现有攻击、Boss 行动、事件效果和准备事务已经形成一条可运行的旧执行链；TurnBasedPack 的 ActionQueue 也是完整权威执行器。零散接入会形成双队列与双提交边界，因此当前不迁移单个步骤；达到响应型效果增长门槛后，应按 `TurnBasedPackIntegrationPlan.md` 一次迁移完整垂直流程。
119. JSON 事件表目前通过运行时创建 `EventData` 兼容旧 EventSystem，能够让内容先读表，但核心仍依赖 Unity ScriptableObject。事件量和跨事件引用增长后，应让 GameCore 消费纯 `EventDefinition`，由 Unity Adapter 只负责表解析与资源引用解析。
120. 通用表源接口已为物品、装备和事件提供统一读取边界，但当前只有事件 Adapter；物品图标、装备属性、配方引用与本地化键仍需先确定稳定 ID 规范，再迁移现有资产，不能仅按显示名称拼接关系。
121. 表驱动事件当前不支持链式事件引用、Boss/物品资产引用和条件表达式。这些字段应通过稳定 ID 在加载阶段二次解析，并输出集中诊断；不要恢复为 JSON 内嵌 Unity 路径或在 View 中查找名称。
122. TurnBasedPack 位于 `Assets` 且本轮直接修复了一行导入源码，重新导入包可能覆盖兼容修改。确定长期采用后，应将包变成有版本号的本地 UPM 依赖或维护可重复应用的补丁，避免 Unity 升级后错误回归。
123. 设计文档同时写有“年龄上限 12”和“超过年龄上限退休”，但没有明确达到 12 当场退休还是再完成一次狩猎后退休。本轮采用后者：`11 → 12` 仍获得成长，下一次狩猎结算时退休且年龄保持 12。正式规则确认后应把退休时点写成唯一案例，避免内容与玩家预期分歧。
124. `HunterAvailabilityState` 当前只有 `Active / Retired`，足以把永久退休与死亡拆开，但未来设施岗位、远征、疗养或事件暂离都可能形成临时不可出战状态。出现第二种临时状态前应先明确“长期身份状态”和“会话占用状态”是否需要两个值对象，不要继续向单一枚举追加互斥含混状态。
125. 退休提交暂时复用 Legacy `HunterManagementSystem` 的装备归还和名册事件，并由 Adapter 同时发布退休事件；这保证当前流程只有一个提交入口，但保存、年鉴、经济反馈仍分散在阶段协调器与管理系统中。统一 `SettlementTransactionCommitted` 落地时，应让不可变退休结果携带装备返还和年鉴记录，由同一事务协调器提交与保存。
126. 退休猎人目前保留在 `Hunters` 历史列表且不占可出战人口上限，长期战役会持续增长；继承、设施工作和退休者事件尚无正式规则。本轮刻意不复用死亡也不删除记录，后续应在读表内容确定后增加只读退休名册/继承接口，而不是让 View 解析年鉴文本或重新激活退休者。
127. 旧 `ScheduleEventForYear` 只写入 AnnalEntry，`GetEventsForYear` 从未消费它，导致表面出现“将发生”但永不到期。本轮已用可执行的 Scheduled 流程替换；长期仍应把历史记录与待执行日程拆成 `AnnalEntry / ScheduledEventState` 两种持久模型，避免一个 `IsCompleted` 同时承担展示与执行状态。
128. Timeline 的 `RandomEventPool` 由于历史命名现在也承载 `Scheduled` 内容，只是在随机抽取时按类别排除。当前行为正确，但内容量增长后应引入按稳定 ID 查询的全事件 Registry，并让随机池、主线池、狩猎池只保存 ID 或只读视图，避免“为了能解析而塞进随机池”的语义漂移。
129. 当前同一稳定事件 ID 同时只允许一个未完成日程，可抵御重复提交和年鉴膨胀，但也明确不支持同事件多个独立发生实例或自循环事件。正式出现周期事件前，应增加持久化 occurrence ID、来源事件 ID 与触发次数限制，而不是放宽现有去重条件。
130. “石脸的回声”及碎石 `+2` 是为验证长期因果链补充的最低内容，全部位于 JSON 表中且不影响通用规则。主线正式定稿后可直接替换文案、延迟和效果；不应把该临时奖励当作最终数值依据。
131. 死亡激励当前使用通用 `UnspentGrowth`，没有实现设计草案中“未知战斗技艺 + 随机属性”的正式内容；这避免提前虚构未定规则。战斗技艺与属性成长表落地后，应让表驱动的 `HunterLossRewardDefinition` 生成奖励计划，不要在 HunterManagement 增加更多内容分支。
132. 当前防献祭规则只要求死者年龄至少 2，仍可能在长期数值上形成养成低价值猎人后主动送死的收益路径。正式平衡时应让激励量受死者累计成长、关系或参战历史约束，并加入灾厄/人口成本；在这些数据存在前不应硬编码复杂倍率。
133. 死亡、退休、招募分别在 HunterManagement 与各 Adapter 中自行写 `RosterChanged` 年鉴，虽已保证各自幂等，但尚无统一名册事务协议。出现复活、失踪或设施岗位前，应提取不可变 `RosterChangeOutcome` 与统一提交器，避免每种状态变化再次复制年鉴、通知和保存顺序。
134. `EventEffectType.KillHunter` 仍未映射到当前 EventSystem 的可执行效果策略，本轮只统一已有的抽卡与战斗死亡入口。正式表格开始配置杀人事件前，应通过窄 `IHunterDeathCommand` 路由到同一死亡事务，并明确目标选择与死亡原因，不能直接写 `IsAlive=false`。
135. 永久损伤目前把属性修正直接结算进猎人持久属性，同时保存稳定损伤 ID；这保证旧架构下读档不重复扣除，但修改目录中的修正数值不会自动迁移既有存档。正式数值稳定前应增加存档版本与迁移规则，长期更适合保存基础属性并在只读快照中汇总损伤修正。
136. 当前每个部位只有一种基础损伤，同一稳定 ID 不允许重复叠加；连续从同一部位存活时可能只增加死亡牌而没有新的永久损伤。内容量增长时应在目录中为每个部位补多个唯一损伤，或明确“可重复层数”模型，不要删除现有幂等保护。
137. 猎人的 `Stats.accuracy` 目前主要供事件、营地展示和未来角色技巧使用，实际武器攻击精准仍来自装备档案；因此“一眼失明”的技巧惩罚尚未改变当前攻击结果牌数量。正式接通角色技巧与武器精准的组合公式时，应让攻击计划读取统一战斗快照并补数值测试。
138. `PermanentWounds` 仍是旧战斗模型中的派生计数，本轮从成功恢复的稳定损伤数量初始化，只用于既有事件与反馈；长期不应同时把它当死亡依据或独立存档真源，权威状态应继续是 `PermanentInjuryIds` 与目录定义。
139. 症状和永久损伤目前都把修正烘焙进持久属性，并额外保存稳定 ID 保障幂等；目录数值改变不会自动迁移旧存档。正式数值稳定前应引入存档版本迁移，长期改为保存基础属性并通过统一 `HunterStatSnapshot` 聚合装备、损伤、症状和特性修正。
140. `Ailments / Traits` 继续保存显示文本以兼容旧事件与 UI，而 `SymptomStates` 使用稳定 ID；症状改名时旧文本不会自动知道新名称。本轮运行时会从结构化状态补齐当前名称，但无法区分需要删除的历史别名，内容管线落地后应给迁移表提供 `formerIds / formerDisplayNames`。
141. 症状目录当前是 ScriptableObject，但 GameCore 与服务只消费纯 `SymptomDefinition`，已经保留未来读表边界。正式批量内容应实现与事件表相同的 `IContentTableSource` Adapter，并在加载阶段集中报告重复 ID、非法阈值和未知效果，不能把 JSON 解析放入规则或 View。
142. “内化后再克服”当前保留内化奖励和两条特性，依据设计草案中的“两者不冲突？”实现最低可玩规则；这仍是未定玩法决策。正式定稿若改为互斥，必须提供已有存档迁移和玩家补偿，而不是只改按钮条件导致历史角色处于非法组合。
143. 症状操作成功后仍由 View 直接保存，与招募、休养、工坊相同地泄漏持久化策略。统一 `SettlementTransactionCommitted` 时应让症状服务返回不可变结果并由阶段协调器处理存档、年鉴、音效和任务观察者。
144. 条件选项当前采用简单 AND 列表并支持逐项取反，足以覆盖正式文档的“门槛后判定”与基础拥有条件，但不能表达 `(A 或 B) 且 C`。内容实际出现第二个 OR 需求时，应升级为可嵌套条件组或规范化表达式树；在此之前不要用复制选项模拟复杂布尔逻辑。
145. 特性、症状、资源和装备条件仍以显示文本为键，沿用当前旧数据模型；改名会让既有事件条件静默失效。内容表规模增长前应为这些内容统一稳定 ID，并由加载期 Registry 解析与集中诊断，View 只显示本地化名称。
146. 条件资格在准备事务时锁定，提交结果时不会再次读取猎人或库存状态。当前事件覆盖层冻结玩家输入且门槛不是消费，因此行为确定；未来加入响应式效果或多人联机后，应让事务保存资格快照版本，或在原子提交中重新验证并返回明确冲突结果。
147. `MinimumResource` 只表达“看见/拥有资源”的门槛，不会消费资源；把它同时当支付条件会造成检查通过但没有扣款。正式付费选项应新增独立、原子的 `SettlementCost` 计划并在提交时消费，不能把 `RemoveResource` 效果当作事务前置扣费。
148. `HunterAdvancementOutcome.ReachedMilestone` 仍按年龄 `2/5/8` 标记，而正式文档同时规定知识与胆识在 `2/5/8` 触发奖励；当前新系统以成长属性为权威，旧字段没有消费者但名称容易误导。整理成长事务时应拆为 `AgeMilestoneReached` 与独立的属性里程碑结果，不能继续共用含混布尔量。
149. 里程碑数值奖励与症状、永久损伤相同，会直接烘焙进猎人持久属性；修改同一稳定 ID 的奖励不会重算旧存档，换新 ID 又会造成重复领取。正式数值调整前应建立版本化奖励迁移表，长期由基础属性与已领取奖励 ID 生成统一属性快照。
150. 当前目录支持特性、意志容量和基础战斗属性奖励，但设计文档允许里程碑触发固定事件。事件奖励尚未加入，避免在没有稳定事件 Registry/事务返回值时反向耦合 Timeline；后续应让定义保存事件稳定 ID，并由里程碑提交结果交给事件路由器调度。
151. 旧存档第一次加载时会追发已跨过的里程碑，保证规则一致；但同步发生在组合根创建反馈 View 之前，因此追发提示不会显示，只能从猎人特性和数值看出变化。正式 Save Migrator 应返回迁移摘要，并在进入营地后统一展示一次版本更新结果。
152. 六项里程碑名称和数值是为完成长期成长闭环补充的基础内容，不代表最终平衡；它们都位于独立目录，可在不改规则代码的情况下替换。内容量增长后应实现里程碑表源 Adapter，并继续让 GameCore 只消费纯定义。
153. 旧存档只有一个全局 `WeaponProficiency`，无法确定历史经验属于哪种武器。本轮采用确定性迁移：第一次获得有效伤害的武器流派继承旧值，后续流派从零开始；正式发布前若能从装备或战斗历史恢复归属，应把该策略升级为有版本号的 Save Migrator 并向玩家展示迁移摘要。
154. 已配置武器通过稳定流派 ID 持久化，未登记的扩展武器会退化为 `weapon:{显示名称}`，保证模组内容仍可获得独立熟练度，但武器改名会生成新记录。内容量增长前应给 Item/Weapon 增加稳定内容 ID，并由武器表 Adapter 把它映射到流派 ID，不能继续把显示文本当长期主键。
155. 武器熟练目录当前是独立 ScriptableObject，GameCore 只消费纯 `WeaponMasteryFamilyDefinition`，已保留读表边界。批量武器与里程碑内容落地时应实现 `IContentTableSource` Adapter，并在加载阶段集中诊断重复别名、重复阈值和未知奖励。
156. 术语文档写“第一武器格为空不增加熟练度”，较新的 Hunter 文档写“空位默认拳头并增加拳头熟练度”；本轮遵循较新文档和现有战斗装配逻辑，将空手映射为 `Fist/拳斗`。规则定稿若改回不增长，只需在 Adapter 的第一武器解析处关闭空手映射，不应修改领域存档模型。
157. 当前 2/5/8 武器里程碑只授予可被事件条件消费的流派特性，未直接改动通用战斗属性，避免换武器后仍错误享受数值加成。正式“战斗共鸣/武器专精”规则确定后，应让战斗快照按当前第一武器流派汇总专属修正，而不是把奖励永久烘焙进通用 Stats。
158. “训练/武器训练”目前使用发明显示名称作为解锁键，并以碎石作为最低可玩成本；具体资源与平衡数值尚未在正式文档定稿。内容表落地时应迁移到稳定发明 ID 和可配置训练配方，不能让 View 或服务继续依赖本地化名称。
159. 训练事务在单线程营地交互中先验证再扣费，熟练度提交失败时会退还资源；未来若出现队列、多玩家或自动训练，应把资源扣除与熟练度增长纳入同一个 Settlement Command/Outcome 提交边界，避免并发状态变化导致检查与提交分离。
160. 当前训练可重复消耗资源，没有每年次数、猎人疲劳或训练上限，因为正式文档只确定“花资源获得武器熟练”。后续平衡规则应通过可持久化训练计划或表配置增加约束，不要在 IMGUI 按钮上维护临时计数。
161. 旧 `GameManager` 在 `Awake` 无条件构建唯一一场 Boss 战，导致狩猎阶段根据实际遭遇注入 `BattleSetup` 已经来不及，连续第二场战斗也没有干净重置边界。该问题已评估为必须重构；完整顺序见 `GameManagerRefactorPlan.md`，后续优先提取每次创建/释放的 `CombatSession`。
162. 多个 View 与行动卡效果仍直接持有或类型判断 `GameManager`，迁移期会保留兼容外观，但新增内容应依赖窄 ReadModel/Command 接口。待现有调用方分批迁移后再删除单例，避免一次性修改所有表现与效果造成高风险回归。
163. 正式可玩入口已经改为 `ProcedureStartGame → GameApp.Entrance → PlayableGameBootstrap.EnsureInstalled`，并移除了早于 ZFramework Procedure 抢跑的 `AfterSceneLoad` 创建路径。Standalone 测试仍走独立引导，不与正式组合根竞争。
164. `GameManager.OnDestroy` 原本会执行全局 `EventBus.Clear()`，从而删除不属于该对象的框架/其他会话订阅；本轮已移除，并在销毁自身时清空 `GameManager.Instance`。应用级清理继续只由 `GameApp.Release` 承担。
165. Play Mode 验证发现项目缺少 TextMesh Pro Essential Resources，Unity 会在运行中尝试导包并报错；本轮已通过 Unity MCP 在编辑模式导入官方基础资源。中文字体资产本身仍需后续内容阶段配置，当前只消除了运行期导入失败。
166. 战斗对象不再在 `GameManager.Awake` 中常驻创建；进入 `BossFight` 时会建立独立 `PlayableCombatSessionScope`，离开时按逆序释放订阅、控制器、可视化与 Unity 根节点。Unity MCP 已验证同一运行会话内连续创建两场战斗时 Boss、角色集合与根节点均为全新实例，旧会话不会残留。
167. 对抗审查发现 `EntityVisualizer` 与 `FlipConditionEvaluator` 原先只订阅不退订，连续战斗会重复响应事件；两者现已实现显式 `Dispose` 并由战斗作用域托管。后续新增会话级 Adapter 必须把订阅释放作为同一生命周期契约的一部分，不能依赖全局 `EventBus.Clear()`。
168. 战斗异步回调现在捕获所属作用域并在等待前后校验当前会话，`BossController` 释放后也不会继续派发剩余行动；重复或跨阶段的 Boss 击败事件会被忽略。单个 `CharacterActionCardEffect.ExecuteAsync` 仍没有取消令牌，因此已经开始的效果内部可能在旧纯对象上完成后才返回；后续扩展响应型效果前应给效果契约增加会话 `CancellationToken`。
